## 現在の中心課題

シミュレーション型コンペに向けた機械学習の勉強から始まり、AIDE全般の進め方への問題意識に広がった。

ユーザーが挙げた懸念は次の四つ。

1. 設計書を作ってから進めるAIDEは、実験で方法を見つける機械学習と相性が悪いのではないか。
2. AIに任せても、成果がユーザー自身の専門知識に依存する面が大きい。
3. ソフトウェア開発でも同じ問題があり、「小さく作る」のが苦手に感じる。
4. これらに加えて、承認の重さも問題に感じる。

直近の論点は、設計の早期固定・分割・承認が重なり、小さく試して学ぶまでの負担を大きくしていないか、という点。

## 会話で示された構造上の懸念

会話中のAIは、AIDEの手順書を確認したとして、以下の規則を挙げた。

- 「子は親の決定を詳細化する。選び直さない」
- 解決法を決めてから機能・実装へ分割する。
- 各段階の決定と分割を人間が承認する。
- 「深さ0〜2は必ず分割する」「葉になるのは深さ3だけ」
- 人間の回答を設計書に入れ、AIの提案の採否を人間が決める。
- 「実装時に決めてよいもの」を委任する欄がある。

これらは添付会話内の報告であり、この保存作業では対象ファイル・版・現在の適用範囲を再確認していない。現行の `harness/`、`harness-v2/`、`v2/` に一律に当てはまるとは扱わない。

会話での見立ては次のとおり。

- 初期の解決法が外れたとき、上位の決定と分割まで戻す必要があり、方式変更の費用が大きくなる。
- 未確認の必要性まで詳細化し、設計を満たすために実装が大きくなりやすい。
- 技術的な採否を人間に尋ねるだけでは、承認者に専門的な正解を知る役割まで求めてしまう。
- 実物がなく判断しにくい → 説明や設計を詳しくする → 決定と承認が増える → 試すまでが遠くなる、という循環が起きうる。

成績不足や開発負担の原因がAIDEだけであることは、比較実験で実証されていない。設計書そのものが機械学習に不向きだと結論したわけでもない。

## 改善の方向として提案されたこと

### 設計書で、実験の枠組みを先に決める

最初から勝つ方式や完成品全体を固定せず、「どう確かめ、何を根拠に次を選ぶか」を設計する。

| 先に合意すること | 実験で選ぶこと |
| --- | --- |
| 目的・評価指標 | 解決方式・モデル・特徴量 |
| 時間・費用・計算予算・期限 | 探索方法・パラメータ |
| 入出力・実行制約 | 機能や戦略の組み合わせ |
| 評価条件・記録方法 | 候補の変更・再実験 |
| 採用・打ち切り条件 | 結果に応じた詳細化 |

設計上も「守る条件」「現在採用している方法」「試している仮説」を区別する。現在の方法は、証拠に応じて委任範囲内で更新できるようにする、という案。

### 次の判断に必要な一作を作る

「小さく作る」は、部品を細分化すること以上に、一度に引き受ける未確認の前提を減らすこと。

通常の詳細設計に入る前に、次の項目だけで試せる経路が提案された。

| 項目 | 内容 |
| --- | --- |
| 今回確かめること | 最も重要な未確認事項を一つ |
| 作るもの | 判断に必要な最小の動作。必要なら入力から結果まで通す |
| 今回扱わないもの | 検証に不要な保存・権限・汎用化など |
| 確認方法 | 誰が、何を使って、何を見て判断するか |
| 作業の上限 | 時間・費用・変更範囲 |
| 結果による次の行動 | 続ける・変える・捨てる条件 |

例: 議事録アプリで最初に確かめるのが抽出品質なら、議事録を貼るとタスク・担当者・期限の表が出るものを作り、実際の議事録3件で使えるか確認する。認証・DB・通知を先に一式作る必要はない。接続可否が最大の不確実性なら、接続だけを試す場合もある。

試作品を捨てる選択肢を残し、本番用の拡張性や共通化は、採用する部分が分かってから整える。固定深度までの分割を試作にも必須としない案だが、規約変更は未実施。

### 人間とAIの役割を分ける

| 人間が決めること | AIに担わせること |
| --- | --- |
| 達成したい目的 | 方法の候補を調べる |
| 時間・費用の上限 | 予算内で比較できる実験を作る |
| 守りたい条件 | 実装・計測・失敗原因の分析 |
| 目的や予算を変更するか | 根拠付きの推奨と不確実性の説明 |

AIは技術的な選択肢を並べて承認を求めるだけでなく、比較結果と限界、次に確かめることまで示すべきだと提案された。

### 承認の対象を変える

承認回数だけを減らすのではなく、最初に合意した作業範囲を後続の判断でも有効にする。

| 行動 | 会話で提案された扱い |
| --- | --- |
| 調査・比較・小さな試作・テスト | 合意した範囲内でAIが進める |
| 元に戻せる実装変更・実験のやり直し | AIが進め、結果を確認できるようにする |
| 目的変更・予算超過・範囲の大幅な拡大 | 人間に判断を求める |
| 公開・送信・重要データの削除など | 影響と既存の許可に応じて承認を求める |

技術的な正しさは、人間の承認を根拠に確定するのではなく、調査・実験・テストで確かめる。設計の更新権限も先に定め、委任された変更は履歴を残して更新できるようにする案。

## 出発点だった機械学習の学習相談

対象としてKaggricultureが挙がった。シミュレーション型コンペは、自分の行動が未来を変える逐次意思決定を扱い、強化学習に探索・最適化・実験評価を組み合わせて学ぶ、という回答だった。

### 提案された学習順

1. Python・NumPy、期待値と分散、訓練と検証、過学習。ニューラルネットワークに進む際に線形代数・微分・勾配降下を補う。
2. MDP・報酬・価値・方策。小さな迷路や在庫管理で価値反復と表形式Q学習を実装する。
3. シミュレータでの先読みと学習の組み合わせ。探索の末端を価値関数で評価する。
4. 小さな離散行動環境でDQN、その後PPO。ルールとの比較、乱数や報酬変更の影響も確認する。
5. 模倣学習、複数の相手での評価、自己対戦、対戦相手への適応。

予測モデル・価値関数・方策・探索は異なる役割を持つ。テープは行動の保存形式であり、それ自体が機械学習とは限らない。

最初から作業員全員の行動を学習させず、「売却量だけ選ぶ」「既存の計画候補から選ぶ」など判断範囲を絞り、手書きルール・探索・学習を比較する案が示された。

### 評価で注意すること

- 同じ試合のターンが訓練と検証に混ざらないよう、試合単位で分ける。
- 途中状態からの最終資金予測は、ログを作った戦略に依存する。
- 単一の相手に勝つことと、複数の相手に広く勝つことを区別する。
- 勝率や最終資金に加え、同じ計算時間での改善を比較する。
- 補助報酬の最適化が最終目的からずれていないか確認する。
- 模倣学習では、誤りから未知の状態へ入った場合も実戦で評価する。

将来の応用として、在庫・生産・人員配置、配送・倉庫、ロボットや設備制御、ゲームAI、AIエージェント、一般的な機械学習開発が挙がった。特に、問題の定式化、比較対象の作成、再現できる実験、改善原因の切り分けが転用しやすい能力として説明された。

教材等としてCS188、Spinning Up、Hugging Face Deep RL Course、Googleの機械学習開発指針、DeepMindの冷却設備制御の技術報告に言及があった。添付にはリンク先がないため、利用時に出典と現行内容の確認が必要。

## 未決事項と再開時の候補

ユーザーが明示したのは問題意識と、このコンテキストの保存依頼。以下の改善案の採用・実装はまだ決まっていない。

- どのAIDEの版・規約を改善対象にするか。
- 試作の入口を既存手順に加えるか、通常設計とは別の経路にするか。
- AIに委任する変更範囲と、人間へ戻す境界をどう記録するか。
- 実験で上位の方法を変更した際、どの文書をどこまで更新するか。
- 効果を確認する最初の小さな機能と、時間・費用の上限。

直前のAI提案は、一つの小さな機能で「最初に作業範囲を合意し、その範囲で試作と検証を進め、動く結果で確認する」を試すこと。測る候補は、承認回数、最初に動くまでの時間、人間が判断に使った時間、手戻り、意図からの逸脱。実施や結果はまだない。

再開時は、承認負担だけを独立した問題として扱わず、早期の方式固定・固定深度の分割・専門知識への依存とのつながりを踏まえて検討する。
