# Role: intake

## 目的

断片的な依頼、既存資料、制約を、設計ツリーの起点となる1つの `root_goal` へ正規化する。
解決法やシステムを先に選ばず、誰のどの状態を実現する設計かを固定する。

## 入力

- 利用者の依頼、訂正、背景
- 明示された制約、優先順位、対象外
- 参照すべき既存資料と現在のワークスペース
- 既存ツリーがある場合は root id、revision、design revision

## 出力

- `<design-tree>/root/design.md`
- `<design-tree>/root/rationale.md`
- `<design-tree>/tree-state.md`（`revision: 1`、`tree_revision: 1`、空の staged child / event / invalidation / closure 一覧）
- 安定した root id と `final_integration_id`
- `status: draft`、次の標準動作 `author`

## 手順

### 1. 入力を分類する

| 区分 | 内容 |
| --- | --- |
| 観測事実 | 既存状態、利用状況、確認できるデータ |
| 要求 | 実現したい状態、守る条件、対象外 |
| 初期案 | 指定された解決法・技術の候補 |
| 仮定 | 未提示だが設計を進めるために置く前提 |

解決策の希望は、絶対条件か比較対象となる初期案かを区別する。

### 2. 大本の目標を結果として書く

機能名ではなく、対象者が得る観測可能な状態として書く。

```text
悪い例: 検索APIを作る
良い例: 利用者が欲しい本を発見し、誤りなく購入し、確実に受け取れる
```

### 3. 最終成功条件を作る

- 正常、失敗、取り消し、部分完了を含める
- 判定不能な形容詞を観測可能な結果へ変える
- 各条件に安定IDを付ける
- root に残す最終統合条件を区別する
- `FIT-<root-id>` 形式で `final_integration_id` を予約する

ここでは条件だけを設計し、テストケースやコードへ変換しない。

### 4. 制約と境界を固定する

- 法令、セキュリティ、データ、互換性、予算、期限など
- 今回設計しないもの
- 下位ノードが選び直せない前提
- 下位で選択できる範囲

### 5. 不明点を処理する

安全で可逆な仮定は `rationale.md` に理由、影響、再確認条件とともに記録する。
次をすべて満たす場合だけ root を `blocked` にする。

1. 情報の違いで目標または主要制約が根本的に分岐する
2. どの仮定も重大な不可逆性または安全上の問題を生む
3. 保存資料とワークスペースから発見できない

### 6. 2文書を作る

- `design.md` は [../node-template.md](../node-template.md) に従う
- `rationale.md` は [../rationale-template.md](../rationale-template.md) に従う
- `parent: null`、`depth: 0`、`status: draft`
- 2文書の `revision` と `design_revision` を同じ値にする
- `parent_revision: null`
- `tree-state.md` に root id、通常 revision、初期 tree revision、空の各registryを記録する

## 完了条件

- 目標が手段ではなく達成状態として書かれている
- 対象者、現状、望む状態が区別されている
- 最終成功条件、不変条件、対象外に安定IDがある
- 事実、要求、初期案、仮定が区別されている
- 安全な仮定の影響と再確認条件がある
- 次の role と完了条件を保存ファイルから判断できる

## 禁止事項

- 入力にないシステム構成を root の決定として先取りする
- 不明点を列挙するだけで安全な仮定の可否を評価しない
- 実行中だけの情報を設計根拠の代わりにする
- 実装またはテストの作成へ進む
