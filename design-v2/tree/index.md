# 設計ハーネス（根）

## 1. これは何を決めるものか

これは設計書をAIと対話的に作るためのハーネス。

## 2. なぜ要るのか

現状人間の把握している機能・システムがなく、そのせいで説明をすることや製品に対し
責任を持つことができない。

> 🧭 **AI**: この答えは、このプロジェクトの目的を「AI に速く実装させること」ではなく
> **「人間が製品に責任を持てる状態を作ること」**に置き換えます。成果物は動く仕組みでは
> なく、人間の把握です。以降の判断はこれを基準にします（速くなるが把握できない案は、
> この目的に対しては失敗）。（2026-08-22）

## 3. 誰が使い、誰が影響を受けるか

とりあえずエンジニア。

## 4. 終わったとどうやって分かるか（受け入れ条件）

（判断を AI に委任。2 の目的「説明できる・責任を持てる」を測れる形にした。
記録: `harness/criteria/precedents.md` 2026-08-25）

- [ ] **把握**: 人間がツリーだけを読んで、何があり、どのノードが何に責任を持つかを
      口頭で説明できる
- [ ] **所在**: 各決定と各境界について、所有者が一意に決まる
      （旧: 「触るノードが一意に決まる」。横断的な機能が複数ノードに散る正常なケースと
      衝突するため、Codex の指摘で 2026-08-25 に改訂）
- [ ] **監査**: 実装 AI が設計に無いことを勝手に決めた箇所を、後から指摘できる
- [ ] **再現**: 新しいセッションでも、Codex でも Claude でも、ツリーと `harness/` を
      渡すだけで同じフローが回る
- [ ] **整合**: ツリーの内容が現在有効であり、欠けているものが分かる
      （古い決定が残っていない。決めるべきで決まっていないものが見える）
      ※ 2026-08-29 追加。split-3 の前検査で「完全に記録・表示・所有・監査された、
      不完全または古いツリーでも目的は達成できない」と指摘されたため

> 💬 **AI**: 4つ目は 7 の「Codex と Claude の両方で使えるか」から立てました。不変条件へ
> 昇格させるか迷いましたが、受け入れ条件として持つほうが検査できるためこちらに置きます。
> （2026-08-25）

## 5. 変えてはいけない前提

祖先から言われた必要な機能を作ること。

根自身の不変条件（継承ではなく著述）:

1. 状態はツリーが持つ。ハーネスは状態を持たない
2. ノードは同型。ただし深さには意味があり、0=根、1=課題、2=解決法、3=システムとする
3. 見てよいのは自分と祖先だけ。兄弟は読まない
4. 子は親を書き換えない。親の修正が必要なら親を別チャットで再開し、必要なら祖先まで戻る
   - 子孫は、直近の親または境界所有者の `## boundary_requests` に**追記だけ**できる。
     `open` の起票は非権威的で、他の子は継承しない

## 6. 決めないこと・任せること

今後の拡張性については決めない。
木の各深さの意味は固定し、分割内容の案は AI に任せる（深さ3・子数5を上限とし、
超える提案はしない）。受け入れ条件と分割条件も AI が案を作るが、決定と分割は人間が
承認する。判断は `harness/criteria/precedents.md` に蓄積し、人間はいつでも覆せる。
分割の提案は AI、承認は人間に固定する。実装（implement）は今回の対象外。

> 🧭 **AI**: 分割・承認・その基準がすべて AI 側にあるため、`precedents.md` が人間の訂正が
> 入る唯一の場所になります。ここが機能しなければ、外から効く力は予算（深さ・子数）だけに
> なります。（2026-08-25）

## 7. 分からないこと・仮置きしていること

当初の3つは解消した。回答をここに残す（チャットには置かない）。

**ハーネスとは何か**: AI を一定の手順に固定する治具。実体は「状態を持たない手順書＋
役割定義」で、それ以上のものではない。実行するのは人間か AI で、ハーネス自身は何も
実行しない。コードが1行も無くても成立する。`harness/` 配下がハーネスの全体。

**どう活用するのか**: セッションを跨いでも同じ手順に乗ること。これが唯一の効用。
新しいチャットで「`harness/README.md` に従って <ノードのパス> を進めて」と言えば同じ
フローが再現する。手順が頭の中にしか無いと、次のセッションで消える（実際、この構想は
一度チャットの中で失われ、過去セッションの記録から復元した）。

**Codex と Claude の両方で使えるか**: 使える。状態がツリー側にあり、ハーネスがただの
Markdown だから。ただし条件が3つある。
1. ツール固有機能（skill / MCP / エディタ拡張）に依存しない。使ってもよいが、無しでも回ること
2. 状態を会話に置かない。ツリーのファイルだけが状態
3. 入口を `AGENTS.md` と `CLAUDE.md` の両方から `harness/README.md` へ張る

3つ目は受け入れ条件「再現」で検査する。

仮置きだった2つを、ここで決定にする（2026-08-29）。

**ブートストラップ例外**: ハーネス自身が未完成の間は、`harness/` への変更を根の決定として
承認せずに直接編集してよい。**終了条件は「深さ1のノードが1つ `children-created` に
なったとき」**。それ以降、`harness/` の変更は根の決定の修正として扱い、再承認を要する。

**版参照の規約**: 承認証跡の内容ハッシュは計算方法（対象範囲・正規化）が未定義のため、
当面は一意な版参照 `<node-id>@<日付>-<種別>-<連番>` を使う（例: `root@2026-08-29-decision-2`）。
ハッシュの計算方法そのものは `authoring` の詳細化対象とする。

## 分割提案 split-4

status: approved（2026-08-29 人間。承認証跡 root@2026-08-29-split-1）

split-3 の切り直し。受け入れ条件を写す（側面で切る）のをやめ、**決定の局面**で切る。

### 前提: 根の decision-2

この提案は `root@2026-08-29-decision-2`（受け入れ条件「整合」の追加、ブートストラップ
例外と版参照規約の決定化）に基づく。**decision-2 は 2026-08-29 に人間が承認済み
（status: active）。**`decision-1` は superseded。

### 子

- `authoring`: **決めたことが残らない・通して読めない・持ち主が決まらない。**
  人間と AI が設計を決める局面の課題
- `handoff`: **実装するとき、設計に無いことが勝手に決まる。**
  設計を使ってコードを書く局面の課題
- `change`: **変わったとき、何が無効になり、何が欠けたままかが分からない。**
  決定が更新される局面の課題

### seam

- id: `s1.closure`
  from: `authoring` / to: `handoff`
  内容: 実装へ渡す設計の閉包。何が揃っていれば実装を始めてよいか

- id: `s2.change-event`
  from: `authoring` / to: `change`
  内容: 変更の単位（決定と境界の一意な ID と版参照）**と、変更が起きたという通知**。
  対象 ID・旧版・新版を含む。`change` は兄弟を読めないため、これが唯一の入力になる

- id: `s3.gap`
  from: `handoff` / to: `authoring`
  内容: 決まっていないことの要求と、実装時に実際に決めた事実の記録要求

- id: `s4.boundary`
  from: `handoff` / to: `change`
  内容: 既存の境界を動かしたいという要求

- id: `s5.invalidation`
  from: `change` / to: `authoring`
  内容: 失効の通知。どの決定が無効になり、書き直しが要るか。
  **欠けている決定の要求も含む**（存在しない決定は失効させられないため、
  「書くべきだが無い」も同じ経路で返す）

- id: `s6.halt`
  from: `change` / to: `handoff`（`halt_ack` は逆向きに返る対の応答）
  内容: 停止の命令と、その受領確認。進行中の実装が古い `s1.closure` を有効と
  信じ続けないようにする。確認が返るまで、変更を確定させない

前回 `s3` として1本に数えていたものは、**宛先が違うので2本**（`s3.gap` と `s4.boundary`）。
書式と搬送路が同じでも、切り口を通る接続は別に数える。

`authoring → handoff → change → authoring` は循環する。**これは欠陥ではなく、決定の
ライフサイクルそのもの**である（split-3 で「循環なし」を長所として書いたのは誤り）。
各 seam は成果物1つの受け渡しであり、兄弟の内部を読む必要は無い。

### 親に残すもの（項目名ではなく、ここで決める）

前回「項目名を並べただけ」と指摘されたので、内容を書く。

1. **正規単位はノード。** 決定の単位も所有の単位もノードであり、表示の単位と同一視しない。
   1ノード = 1ディレクトリ = 1つの `index.md`。
   帰結として、**1ノード内の決定はすべて同じ所有者を持つ**。所有者を分けたければ
   ノードを分ける
2. **`index.md` の書き込み所有権**
   - `## 親からの振り分け` — 親だけが書く
   - 本文（1〜7）— そのノードの担当（そのノードを対象にしているチャットの AI と人間）
     だけが書く
   - `## 分割提案` — 提案した AI が書き、前検査が追記する
   - `## boundary_requests` — 子孫が追記のみ
   - `## 承認証跡` — 人間（review）だけが書く
   - frontmatter の `status` — 状態を進めた役割が書く。ただし `stale` は change の判定に
     基づき review が書く
   - frontmatter の `children` / `seams` — 親が分割承認後に書く
   - frontmatter の `uses_seams` — 親が振り分けとして書く。子は書き換えない
   - frontmatter の `id` / `parent` / `depth` — 親が子作成時に書く
   - `status` の書き手（状態ごとに一意にする）
     | 状態 | 書き手 |
     | --- | --- |
     | `draft` / `questions-done` | そのノードの担当 |
     | `decision-approved` / `split-approved` / `rejected` / `stale` | 人間（review） |
     | `split-proposed` | 提案した AI |
     | `split-prechecked` | 前検査した AI |
     | `children-created` / `done` | 親 |
   - すべての seam 成果物 — **親の `## seam_inbox` に追記する**（下記10）
3. **共通語彙**
   - *ノード*: 1つの決定のまとまり。`index.md` 1枚で表される
   - *決定*: そのノードで確定した内容。人間の承認を経たもの
   - *seam*: 兄弟同士の接続。親だけが定義できる
   - *閉包*: 自ノード＋祖先チェーンの `index.md`。実装や対話に渡す単位
   - *承認*: 人間が決定または分割を確定する行為。2種類あり互いに代用しない
4. **版参照の規約**: ハッシュの計算方法が未定義のため、当面は
   `<node-id>@<日付>-<種別>-<連番>` の一意な参照を使う（例: `root@2026-08-29-decision-2`）
5. 目的、受け入れ条件（4＋整合）、不変条件4つと `boundary_requests` の例外
