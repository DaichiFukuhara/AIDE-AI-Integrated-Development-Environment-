## 1. これは何を決めるものか

<!-- 深さ1: 課題の範囲と、それに対する解決法 -->

**課題**: 決定が変わったとき、その変更に依存していた他の決定が古いまま残り、誰も
気づかない。

**解決法（原理）**: 入力を `s2.change-event` と `s4.boundary` の2つに限定し、
**「入力封筒＋参照するツリーの版」から失効集合を決める純粋な関係**を定義する。
そのうえで、次の安全な順序で失効を確定させる。

```
s6.halt（停止）を降ろす → halt_ack が揃う → review が status: stale を書く
  → s5.invalidation を返す → 人間の decision 承認（＝確定）
```

提案が却下・撤回され、その閉包を止めている理由がひとつも残っていない場合は、
**`s6.halt`（再開）を降ろして元の閉包での続行を許す**
（`root@2026-08-31-decision-4` 案。有効な停止要因が残る間は再開しない）。

根の `harness/README.md` は既に失効範囲の表を持っている（seam が変わったら `uses_seams` で
名指しする子と子孫／責任範囲・owns・受け入れ条件の割り当て・書き込み権限が変わったら
対象の子と子孫すべて）。**`change` はこれを選び直さず、適用順序と適用条件を詳細化する。**

**分類不能な変更は勝手に補完しない。**「判定不能」として確定を止め、`boundary_request` で
root へ返す（根の表は seam と責任範囲しか分類していないが、`s2` は一般の決定変更も含む。
Codex の指摘 2026-08-30）。

`s4.boundary` の受領は「変更が起きたあと」ではなく**変更前の局面**であり、
`change` はこの2つの局面を両方持つ。

## 2. なぜ要るのか

変更は必ず起きる（`boundary_request`、人間の翻意、実装からの gap）。影響範囲を人手で
追うと漏れる。根の前検査で「完全に記録・表示・所有・監査された、不完全または古いツリー
でも目的は達成できない」と指摘され、受け入れ条件「整合」が追加された経緯がある。

## 3. 誰が使い、誰が影響を受けるか

- **使う**: 設計を変更する人間と AI
- **影響を受ける**: `s5.invalidation` を受け取る側、`s6.halt` を受け取る側

## 5. 変えてはいけない前提

すべて根から継承。このノードで選び直さない。出所は `root@2026-08-29-decision-2`（本文1〜7）と
`root@2026-08-31-decision-3`（split-4 の seam 定義・子ごとの振り分け・共通語彙）の2つで、
下の各項目のうち共通語彙・確定の定義・封筒と搬送路は decision-3 側から来ている。

1. 不変条件1〜4 と `boundary_requests` の例外
2. **根の失効範囲の表**。粗すぎると感じても `change` が独自に調整してはいけない。
   疑義は質問7に残し、変えるなら root へ `boundary_request`
3. 封筒の最小項目。seam の搬送は必ず親経由
4. `payload` の記録・直列化形式は `change` の担当ではない
5. 正規単位はノード。版参照規約。共通語彙
6. **`stale` は change の判定に基づき review（人間）が書く**、という書き込み権限
7. **`halt_ack` が返るまで変更を確定しない**。
   **「確定」は根が定義済み**（`root@2026-08-31-decision-3`）: 変更後の版が
   「現在有効な決定」になること＝人間の decision 承認により `status: active` に
   なる時点。したがって **`halt_ack` は人間の承認より前に揃っていなければならない**。
   ack 不達時にタイムアウトや強制確定を置くことは根に反する。
   「`pending` のまま」が唯一整合する回答であり、別の回復方針が要るなら root を再開する。
   あわせて `s2.change-event` は**未承認案が起票された時点で発火**する（確定より前）
8. 状態はツリーが持つ。判定はイベント単体ではなく「イベント＋参照ツリー版」に対して行う
9. 予算（深さ3・子数5）、ツール固有機能に依存しないこと
