## 1. これは何を決めるものか

<!-- 深さ1: 課題の範囲と、それに対する解決法 -->

### 課題の範囲（親の振り分けより所与。ここでの決定対象ではない）

**設計を決める局面** —— あるノードについて人間と AI が内容を決め、人間が承認し、
子へ降ろすまでの区間。実装する局面（兄弟 `handoff`）と、決定が変わる局面
（兄弟 `change`）は含まない。

### 解決法（interview Q1 の回答。2026-08-29 人間が選択）

**検査を先に決め、書式をそれに従属させる。**

「通して読めるか / 所有者が一意か / 欠けが見えるか / cold start で再現するか」を、
ツリーと `harness/` だけを入力として、人間でも AI でも実行でき**合否が一意に決まる
検査手順**として先に定義する。ノードの書式は、その検査を通すために必要な分だけ決める。

この解決法は、次の2つを規則として含む。

- **検査できない書式規則は作らない。** 守られているか確かめられない規約は守られない
- **検査できない受け入れ条件は書かない。** 根が「満足できたら終了」を却下したのと同じ理由
  （`harness/criteria/precedents.md` 2026-08-25）

> 💬 **AI**: 案は AI が3つ出し（検査先行 / 書式先行 / 検査のみ）、人間が「検査を先に決め、
> 書式を従属させる」を選びました。選択そのものは人間のもので、上の本文は AI が書いた
> 案文です（`harness/roles/interview.md`「人間の答えはそのまま書く」への注記）。
> （2026-08-29）

> 🧭 **AI**: この解決法を採ると、深さ2の分割は「検査項目ごと」に切りたくなります。
> しかしそれは根の split-3 が取り下げられた切り方（受け入れ条件をそのまま写す）と
> **同型**であり、条件に現れない課題が落ちて seam が増えます。分割提案では、この罠を
> 明示的に比較対象へ入れます。（2026-08-29）

## 2. なぜ要るのか

祖先から継承（出所: 根の 2）: 現状人間の把握している機能・システムがなく、そのせいで
説明をすることや製品に対し責任を持つことができない。

この局面での具体形（出所: 根の split-4 の子定義と、受け入れ条件の割り当て）:

1. **残らない**: 決めたことが会話に閉じ、ファイルに残らない。次のセッション・別モデルで
   再開できない
2. **通して読めない**: 残っていても、量と構造の問題で通して読めず、人間が全体を説明できない
3. **持ち主が決まらない**: どの決定・どの境界が誰のものか決まらない
4. **欠けが見えない**: 決めるべきなのに決まっていないものが、ツリーを読んでも分からない

> 🧭 **AI**: 4 は根の受け入れ条件「整合」のうち**欠落の側**として `authoring` へ
> 割り当てられたものです。鮮度（古い決定が残っていないこと）は兄弟 `change` の担当で、
> ここでは扱いません。両者の論理積は、子が全部 `done` になった時点で根が再検査します
> （根の「親に残すもの」12）。（2026-08-29）

> ➕ **AI**: 1〜4 は仮説ではなく、**このツリー自身で観測できます**。根の `index.md` は
> 650 行あり、その大半が却下・取り下げ済みの分割提案（split-1 / split-2 / split-3）です。
> 現在有効な決定（`root@2026-08-29-decision-2` と split-4）を読み取るには、無効な提案を
> 読み飛ばす必要があります。受け入れ条件「把握」は、木の最初のノードで既に満たされて
> いません。（2026-08-29）

## 3. 誰が使い、誰が影響を受けるか

祖先から継承（出所: 根の 3）: とりあえずエンジニア。

この局面での内訳:

- **使う**: そのノードを対象にしたチャットの AI（interview / split）、前検査する別実装の
  AI（precheck）、承認する人間（review）
- **影響を受ける**: 後からツリーだけを読んで製品を説明する人間。および seam 経由で
  `authoring` の出力を受け取る兄弟（`s1.closure` / `s2.change-event`）。
  兄弟の内部設計は読まない

## 4. 終わったとどうやって分かるか（受け入れ条件）

（判断を AI に委任。根の 6「受け入れ条件と分割条件も AI が案を作るが、決定と分割は人間が
承認する」に基づく。記録: `harness/criteria/precedents.md` 2026-08-29）

親から割り当てられたのは 把握 / 所在 / 再現（記録の側）/ 整合（欠落の側）の4つ。
Q1 の解決法（検査を先に決め、書式を従属させる）に対して検査可能な形にした。

**解決法そのものが成立したか**

- [ ] **検査可能**: 割り当てられた4条件それぞれに、ツリーと `harness/` だけを入力とし、
      人間が読んでも AI が読んでも**同じ合否になる**検査手順が定義されている
      （合否が読み手によって割れる項目が0件）
- [ ] **書式の従属**: ノードの書式規則が1つ残らず、いずれかの検査項目に紐づいている。
      **どの検査にも紐づかない書式規則が0件**であり、逆に**検査だけあって書式で
      支えられていない項目も0件**
- [ ] **自己適用**: 定義した検査を、このツリー自身（根と `authoring` の部分木）へ実際に
      通し、結果が記録されている。現に根の `index.md` は「把握」に落ちる（2 の観測）。
      落ちたまま合格にしない

**割り当てられた4条件**

- [ ] **把握**: 「ツリーだけを読んで、何があり、どのノードが何に責任を持つかを口頭で
      説明できる」ことを測る検査が定義され、対象の全ノードが合格する
- [ ] **所在**: 任意の1つの決定と任意の1つの境界について、所有者（＝その節を書ける役割）が
      一意に答えられる。答えが**0個または2個以上になる箇所が0件**
- [ ] **再現（記録の側）**: cold start の1行
      （`harness/README.md` に従って <ノードのパス> を進めてください）だけで、別セッション・
      別モデルでも検査の合否が一致する。会話にしか無い情報を必要としない
- [ ] **整合（欠落の側）**: 「決めるべきだが決まっていない」もの（未回答の固定質問、
      `provisional`、未割り当ての受け入れ条件、`deferred`、`open` の boundary_request、
      祖先から委譲された宿題）を、ツリーを読むだけで**列挙できる**。検査はその列挙に
      漏れが無いことを判定する

> 🧭 **AI**: 「鮮度」（古い決定が残っていないか）はここに書きません。兄弟 `change` の
> 担当であり、論理積の再検査は根が行います（根の「親に残すもの」12）。（2026-08-29）

## 5. 変えてはいけない前提

すべて祖先から継承（出所を明記する）。この節に `authoring` 自身の著述は無い。

**根の不変条件 1〜4**（出所: 根の 5）

1. 状態はツリーが持つ。ハーネスは状態を持たない
2. ノードは同型。ただし深さには意味がある（0=根 / 1=課題 / 2=解決法 / 3=システム）
3. 見てよいのは自分と祖先だけ。兄弟は読まない
4. 子は親を書き換えない。`boundary_requests` への追記だけが例外で、`open` は非権威的

**ツール非依存**（出所: 根の 7）: skill / MCP / エディタ拡張に依存しない。Codex でも
Claude でも、Markdown を読めば同じ手順が回ること。

**根の「親に残すもの」1〜12**（出所: 根の split-4。振り分けが 1〜12 と指定）。
うち `authoring` の設計を直接拘束するもの:

- 1: **正規単位はノード。** 1ノード = 1ディレクトリ = 1つの `index.md`。表示の単位と
  同一視しない。1ノード内の決定はすべて同じ所有者を持つ
- 2: `index.md` の**節ごとの書き込み所有権**と、`status` の書き手の表
- 3: 共通語彙（ノード / 決定 / seam / 閉包 / 承認）
- 4: 版参照の規約 `<node-id>@<日付>-<種別>-<連番>`
- 9: seam の搬送は必ず親を経由する。送り手は親の `## seam_inbox` へ追記し、親が権威化する
- 10: 封筒の最小項目（`seam` / `from` / `from_ref` / `target` / `date` / `status` /
  `payload`）。**`payload` の書式は親では決めない = `authoring` が決める**
- 12: 「整合」は欠落（`authoring`）と鮮度（`change`）の論理積。統合再検査は根が行う

**承認の2種**（出所: 根 / `harness/README.md`）: 決定の承認と分割の承認は互いに代用しない。
提案は AI、前検査は別実装の AI、承認は人間。

**予算**（出所: 根）: 最大深さ3、1ノードあたり最大子数5。

**seam**（出所: 親の振り分け）

- 使う: `s3.gap`（handoff →）、`s5.invalidation`（change →）

## 6. 決めないこと・任せること

（interview Q6 の回答。2026-08-29 人間が選択）

**`authoring` が決めるのは、規約（書式）と検査までである。**
検査に落ちている既存ノードを実際に直す作業は、そのノードの担当へ任せる。根が落ちて
いるなら、根を別チャットで cold start し、根自身として直して決定の再承認を取る。
`authoring` が負うのは「どのノードが、どの検査に、なぜ落ちているか」を示すところまで。

> 🧭 **AI**: この線引きは不変条件4（子は親を書き換えない）と一致します。遡及適用まで
> `authoring` の責任にすると、深さ1のノードの完了が祖先の再承認待ちになり、自分だけでは
> 閉じられなくなります。（2026-08-29）

**深さ2以降へ降ろすもの**（AI の判断。根の 6「分割内容の案は AI に任せる」に基づく）

- 検査手順の文面（入力・実行順・合否の書き方）
- ノード書式の細部（節の並び、マーカーの記法、要約の置き場）
- **承認証跡のハッシュ計算方法**（対象範囲と正規化）。根の 7 が `authoring` へ委譲した宿題。
  深さ1では根の決定（当面は版参照 `<node-id>@<日付>-<種別>-<連番>` を使う）をそのまま
  引き継ぎ、ハッシュの定義は深さ2以降で決める
- `s1.closure` / `s2.change-event` の `payload` の書式。根の「親に残すもの」10 が
  「`payload` の書式は親では決めない」として `authoring` へ残したもの
- 「把握」の合否を一意にするための代理指標の具体（7 を参照）

**実装（implement）へ任せるもの**

- **検査の実行手段。** 祖先から継承（根の 7）: ツール固有機能に依存しないこと。
  スクリプトを書いてもよいが、**無くても人手で同じ合否が出せること**。
  スクリプトの有無そのものは `authoring` では決めない

**そもそも扱わないもの**（出所: 祖先。ここでの判断ではない）

- 実装役（implement）は根の 6 で対象外
- 兄弟の内部（`handoff` / `change` の解決法）
- 鮮度・失効の判定（`change` の担当）。「整合」のうち欠落の側だけを見る

## 7. 分からないこと・仮置きしていること

**仮置き（provisional）**

- **承認証跡のハッシュ計算方法**: 対象範囲と正規化が未定義。根の 7 が `authoring` へ
