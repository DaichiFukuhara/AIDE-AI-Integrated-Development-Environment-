## 2. なぜ要るのか

祖先から継承（出所: 根の 2）: 現状人間の把握している機能・システムがなく、そのせいで
説明をすることや製品に対し責任を持つことができない。

この局面での具体形（出所: 根の split-4 の子定義と、受け入れ条件の割り当て）:

1. **残らない**: 決めたことが会話に閉じ、ファイルに残らない。次のセッション・別モデルで
   再開できない
2. **通して読めない**: 残っていても、量と構造の問題で通して読めず、人間が全体を説明できない
3. **持ち主が決まらない**: どの決定・どの境界が誰のものか決まらない
4. **欠けが見えない**: 決めるべきなのに決まっていないものが、ツリーを読んでも分からない

> 🧭 **AI**: 4 は根の受け入れ条件「整合」のうち**欠落の側**として `authoring` へ
> 割り当てられたものです。鮮度（古い決定が残っていないこと）は兄弟 `change` の担当で、
> ここでは扱いません。両者の論理積は、子が全部 `done` になった時点で根が再検査します
> （根の「親に残すもの」12）。（2026-08-29）

> ➕ **AI**: 1〜4 は仮説ではなく、**このツリー自身で観測できます**。根の `index.md` は
> 650 行あり、その大半が却下・取り下げ済みの分割提案（split-1 / split-2 / split-3）です。
> 現在有効な決定（`root@2026-08-29-decision-2` と split-4）を読み取るには、無効な提案を
> 読み飛ばす必要があります。受け入れ条件「把握」は、木の最初のノードで既に満たされて

## 5. 変えてはいけない前提

すべて祖先から継承（出所を明記する）。この節に `authoring` 自身の著述は無い。

**根の不変条件 1〜4**（出所: 根の 5）

1. 状態はツリーが持つ。ハーネスは状態を持たない
2. ノードは同型。ただし深さには意味がある（0=根 / 1=課題 / 2=解決法 / 3=システム）
3. 見てよいのは自分と祖先だけ。兄弟は読まない
4. 子は親を書き換えない。`boundary_requests` への追記だけが例外で、`open` は非権威的

**ツール非依存**（出所: 根の 7）: skill / MCP / エディタ拡張に依存しない。Codex でも
Claude でも、Markdown を読めば同じ手順が回ること。

**根の「親に残すもの」1〜12**（出所: 根の split-4。振り分けが 1〜12 と指定）。
うち `authoring` の設計を直接拘束するもの:

- 1: **正規単位はノード。** 1ノード = 1ディレクトリ = 1つの `index.md`。表示の単位と
  同一視しない。1ノード内の決定はすべて同じ所有者を持つ
- 2: `index.md` の**節ごとの書き込み所有権**と、`status` の書き手の表
- 3: 共通語彙（ノード / 決定 / seam / 閉包 / 承認）
- 4: 版参照の規約 `<node-id>@<日付>-<種別>-<連番>`
- 9: seam の搬送は必ず親を経由する。送り手は親の `## seam_inbox` へ追記し、親が権威化する
- 10: 封筒の最小項目（`seam` / `from` / `from_ref` / `target` / `date` / `status` /
  `payload`）。**`payload` の書式は親では決めない = `authoring` が決める**
- 12: 「整合」は欠落（`authoring`）と鮮度（`change`）の論理積。統合再検査は根が行う

**承認の2種**（出所: 根 / `harness/README.md`）: 決定の承認と分割の承認は互いに代用しない。
提案は AI、前検査は別実装の AI、承認は人間。

**予算**（出所: 根）: 最大深さ3、1ノードあたり最大子数5。
