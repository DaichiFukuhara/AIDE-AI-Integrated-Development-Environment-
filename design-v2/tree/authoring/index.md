## 1. これは何を決めるものか

<!-- 深さ1: 課題の範囲と、それに対する解決法 -->

**課題**: 人間と AI が設計を決めるとき、決定がツリーに残らず、残っても通して読めず、
誰のものか決まらず、決めるべきで決まっていないものが見えない。

**解決法（原理）**: 設計を決める局面に**正規の著述モデル**を1つ置く。次の5点からなる。

1. AI が書いた文章は、**起草者を明記した未承認案**として記録される
2. **人間の承認後だけ「決定」になる**
3. 決定の**正本は所有者ノード1か所だけ**に置き、他の場所には版参照だけを置く
4. 決めるべき事項は `未決` / `仮置き` / `委任済み` / `決定済み` のいずれかの状態を持つ
5. `s1.closure` と `s2.change-event` の payload は、**同じ正本から導出**する。
   `s2` は単発の通知ではなく**変更提案のライフサイクル通知**
   （`起票` / `差し替え` / `却下` / `撤回` / `承認`）なので、payload は
   どの事象かを区別できなければならない（`root@2026-08-31-decision-4` 案）

子（深さ2）はこの5点を詳細化するのであって、選び直さない。

## 2. なぜ要るのか

いま決定はチャットの中で起き、ファイルに残るのは結論の一部だけ。実際に v2 の構想自体が
一度チャットの中で失われ、過去セッションの記録から復元している。残っていても量と順序の
問題で通して読めない。人間が決めたのか AI が決めたのかが区別されない。決めるべきなのに
決まっていないものは、そもそも見えない。結果として根の 2（人間が説明できず、責任を
持てない）が起きる。

## 3. 誰が使い、誰が影響を受けるか

- **使う**: 設計チャットの AI（起草・記録）と人間（決定・承認）
- **影響を受ける**: `s1.closure` を受け取る側、`s2.change-event` を受け取る側、
  および将来この設計を読む人間

## 4. 終わったとどうやって分かるか（受け入れ条件）

## 5. 変えてはいけない前提

すべて根から継承。このノードで選び直さない。出所は `root@2026-08-29-decision-2`（本文1〜7）と
`root@2026-08-31-decision-3`（split-4 の seam 定義・子ごとの振り分け・共通語彙）の2つで、
下の各項目のうち共通語彙・確定の定義・封筒と搬送路は decision-3 側から来ている。

1. 不変条件1〜4 と `boundary_requests` の例外
2. **正規単位はノード**。所有モデルは根が確定済みで、`authoring` は記録と表示の方法だけを
   決める（所有単位の再定義は担当外）
3. `index.md` の書き込み所有権表と、`status` の書き手表
4. 共通語彙。とくに**人間の承認を経ていないものは「決定」ではない**（「未承認案」と呼ぶ）
5. **版参照の形式** `<node-id>@<日付>-<種別>-<連番>` は根が固定済み。委譲されたのは
   ハッシュの計算方法であって、版参照形式の再決定ではない。ハッシュで置換したいなら
   `boundary_request` を要する
6. 提供する `s1.closure` / `s2.change-event` の**封筒項目は親が固定済み**。
   このノードの担当は `payload` の意味と書式だけ
7. 予算（深さ3・子数5）、ツール固有機能に依存しないこと（Codex / Claude の双方で回る）
8. 根の受け入れ条件「再現」は「ツリーと `harness/` を渡すだけで回る」であり、
   「閉包のファイルだけ」ではない

## 6. 決めないこと・任せること

<!-- 委任は「自由に選べる範囲 / 守る制約 / 再承認が必要になる境界」の3点を必ず付ける
     （Codex の指摘 2026-08-30。「細かい記法は任せる」は広すぎて委任にならない） -->

### 委任してよいもの

| 自由に選べる範囲 | 守る制約 | 再承認が必要になる境界 |
| --- | --- | --- |
| 改行・字下げ・説明文の文体 | 機械列挙の対象になる節見出しは変えない | 節見出し自体を変えるとき |
| 検査器の実装言語 | 検査器が無くても人手で同じ判定に至れること | 検査器の判定が人手判定と食い違うとき |
| 人手検査かスクリプト検査か | ツール固有機能に依存しない | どちらかを必須にするとき |

### 委任してはいけないもの（このノードまたは子で決める）

- 状態区分（`未決` / `仮置き` / `委任済み` / `決定済み`）と、各状態の必須項目
- 正本と版参照の区別
- `s1.closure` / `s2.change-event` の `payload` の意味
- ハッシュの対象範囲と正規化

### 担当外（他ノードの責任）

- 失効の判定そのもの。ただし、受け取った `s5.invalidation` を**著述上の未決・書き直し
  対象としてどう表すか**は `authoring` の担当
- 実装時の逸脱検出

## 7. 分からないこと・仮置きしていること

- **ハッシュの計算方法**（根から委譲）。対象範囲・正規化・アルゴリズムが未定義。
  深さ2で決める
- 「通して読める」量の上限を数値（1ノードあたりの行数など）で決めるか、
  受け入れ条件「把握」の実地テストだけで担保するか
- 決定義務の発生源をどこまで列挙するか。現時点の候補は
  「固定質問7つ / 親からの振り分け / 受信した seam / 承認済み分割が生む子」の4つで、
  これで尽きているかは未確認。
  **解決者: `authoring.node`（分割承認後）。**初期値として4つを渡し、増減させる。
  増減は `authoring.node` の決定として人間の承認を要する

### 他の切り方との比較

- **3分割案（record / completeness / closure）**: `record`（1件の書式）と
  `completeness`（母集団と未決の表現）が**どちらもノード1枚の形式を決める**ため、
  書き込み所有権を親へ上げる必要が生じた。split-1 が却下された
  「同じ `index.md` を複数の子が書く」型と同じ。
  この案で必要になる seam は次の3本（precheck v1 軽微1 の要求により列挙。
  現案の双方向2本と比較できる）:
  - `record` → `completeness`: 決定1件の状態区分（`completeness` はこの状態で全件を数える）
  - `record` → `closure`: 決定1件の表現（`closure` はこれを束ねる）
  - `completeness` → `closure`: 実装開始可能かの判定に要る充足条件
  加えて、`record` と `completeness` の**書き込み所有権表**を親が持つ必要がある。
  現案はこの表そのものを不要にする（「親に残すもの」3 で `node` の単独所有にした）
- **受け入れ条件で切る案（把握 / 所在 / 再現 / 整合）**: split-3 が根で却下された型。
  条件は割り当て先であって課題ではない
- **分割しない案**: 深さ0-2は必ず分割する。加えて、2子は**検査方法が違う**。
  `node` は人間の通読テストと母集団の列挙で測り、`closure` はテストベクトルと
  cold start テストで測る
- 子2つ、seam 2本、深さ2。予算（深さ3・子数5）内
