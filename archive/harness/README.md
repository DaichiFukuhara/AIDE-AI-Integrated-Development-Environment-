# 設計ハーネス

> 旧版の保存先です。最新版は [harness-v2](../../harness-v2/README.md) を参照してください。この版のパス表記は `archive/` を基準に読み替えます。

AIDE v2 を、アプリケーションではなく**規約と役割**として書いたもの。
watcher も UI も無い。人間と AI がこの文書に従って動けば、それがハーネスである。

## 原則

- **状態はツリーが持つ。ハーネスは持たない。** 設計ツリーのファイルが唯一の正で、
  この `harness/` 配下は手順書にすぎない。どのモデル・どのセッションからでも、
  ツリーを読めば途中から入れる。
- **設計書と記録は別のファイル。** ノードは設計書 `index.md` と記録 `record.md` の
  2枚を持つ。設計書に置くのは**現在有効な決定だけ**で、対話・分割提案・前検査・
  承認証跡・取り下げた案・改訂の経緯は記録へ置く。設計書だけを読んで設計と実装が
  できる状態を保つ（[設計書と記録を分ける](#設計書と記録を分ける)）。
- **ノードはすべて同じ形をしている。** ただし深さには意味がある。
  深さ0は根（ペイン・目的）、深さ1は課題、深さ2は解決法、深さ3は具体的なシステム。
  ノードの形式は共通のまま、何を決めるかが深さによって変わる。
- **見てよいのは、自分と祖先だけ。** 兄弟の設計書は読まない。兄弟との接続は
  共通の親が seam として持つ。
- **子は親を直接書き換えない。** 親の修正が必要なら、その親を別チャットで再開して
  親自身として書き換える。親だけで決められなければ、同じ手順で必要な祖先まで戻る。
- **1チャット = 1ノード。** 1つのチャットで扱う対象ノードは1つだけ。分割が承認されたら、
  子は**別のチャットで話す**。同じノードについて複数のチャットが立つことはある
  （提案と前検査は別チャット）。逆に、1つのチャットが複数ノードを跨ぐことは無い。

## ツリーの形

```
<root>/
  index.md                 根の設計書
  record.md                根の記録
  <child>/
    index.md
    record.md
    <grandchild>/
      index.md
      record.md
```

ディレクトリがそのまま木。1ノードは設計書 `index.md` と記録 `record.md` の2枚。
ひな型は [node-template.md](node-template.md) と
[record-template.md](record-template.md)。`record.md` は最初に何か記録するときに作る。

**ツリー全体の設計書は、`index.md` を木の順に読んだものである。**
統合した1枚のファイルは作らない。複製は必ず本体とずれる。

## 深さごとの意味

| 深さ | ノードが表すもの | そのチャットで決めること | 子として作るもの |
| --- | --- | --- | --- |
| 0 | 根 | ペイン、目的、利用者、成功条件、不変条件 | 課題 |
| 1 | 課題 | 課題の具体化と、その課題に対する解決法 | 解決法 |
| 2 | 解決法 | 親の決定の詳細化と、それに伴う機能 | 機能ごとの実装単位 |
| 3 | システム | 実装可能な境界、振る舞い、受け入れ条件 | 作らない。実装へ渡す葉 |

固定質問7個は全ノードで同じ形式を使う。ただし質問の対象は深さによって変わる。
たとえば「これは何を決めるものか」は、深さ1では課題と解決の範囲、深さ2では解決法の
詳細と機能、深さ3では実装するシステムを指す。

- **葉になるのは深さ3だけ。**深さ0-2は必ず分割する。
- **子が1つでも分割する。**各深さに固有の定義があり、飛ばすとその深さの決定が
  どのノードにも属さなくなる。子が1つの分割は、抽象度を1段下げる作業そのものであり、
  同じ内容の移し替えではない。
- **子は親の決定を詳細化する。選び直さない。**別案にしたければ `boundary_request`。
- 深さ3が1つの実装単位として大きすぎたら、その場で分割せず深さ2へ差し戻す。

## 設計書と記録を分ける

**設計書（`index.md`）に書けるのは、現在有効な決定だけである。**
どう決まったか（対話・提案・指摘・却下された案・改訂の経緯）は記録（`record.md`）へ置く。

分ける理由は、設計書が「何を作るか」を読む文書だからである。1枚に混ぜると、
決定1に対して経緯が10行付き、読む側が現在有効な決定を毎回探し直すことになる。
承認を重ねるほど読みにくくなるなら、その承認列は目的を果たしていない
（[承認の原則](#承認の原則)）。

### どちらに書くかの判定

> **その文を消したとき、作るものが決まらなくなるか。**
> - なる → 設計書
> - ならない（分からなくなるのは「なぜそう決めたか」だけ） → 記録

| 内容 | 置き場 |
| --- | --- |
| 固定質問1〜7の答え（現在有効な版） | 設計書 |
| 親からの振り分け | 設計書 |
| 承認された構成（子・seam・親に残すもの・受け入れ条件の割り当て） | 設計書 |
| 受理された `boundary_request` の結果（新しい制約・seam） | 設計書 |
| 権威化された seam 成果物 | 設計書 |
| AI の提案・問い返し・検討（`❓` `💬` `➕` `🔀` `🧭`） | 記録 |
| 分割提案（承認前のもの・却下・取り下げを含む） | 記録 |
| 前検査の指摘と判定 | 記録 |
| 承認証跡（誰がいつ何を承認したか、重大指摘を残した理由） | 記録 |
| 改訂の経緯（「旧: …」「…の指摘で改訂」「※ …を追加」） | 記録 |
| `open` の `boundary_request`、未権威化の `seam_inbox` | 記録 |

判断に迷ったら記録へ落とす。記録は消えないので、必要だと分かった時点で設計書へ上げ直せる。
逆向き（設計書に置いたまま様子を見る）は、設計書が読みにくくなる方向にしか働かない。

### 承認が、記録から設計書への唯一の門

- 記録に書かれたものは**提案にすぎない**。人間の承認を通ったものだけが設計書に載る。
- 承認したその場で昇格させる。「記録側だけ更新済み」の状態を残さない。
- 昇格した内容は版参照（`<node-id>@<日付>-<種別>-<連番>`）で記録と結ぶ。現在有効な版は
  frontmatter の `decision_ref` / `split_ref` に置き、本文には書かない。
  **設計書に経緯を書く代わりに、版参照で記録を引けるようにする。**
- **記録は権威を持たない。**設計書と食い違ったら設計書が正。
- **記録は後から書き換えない。**追記だけ（`結果` の追記と `status` の更新を除く）。
- **設計書は追記しない。**決定が置き換わったら、その箇所を書き換える。
  古い版は記録が持っているので、設計書に「旧: …」を残さない。
  この2つが逆になると、両方が履歴になって設計書が消える。

### 設計書に書かないもの

- 履歴の痕跡（「旧: …」「2026-08-25 に改訂」「※ …の指摘で追加」）→ 版参照に置き換える
- 却下・取り下げ・失効した案
- AI 自身の発言
- 手続きの進行状況（frontmatter の `status` を除く）

## フロー

### 1. 根を構成する

1. 固定質問7個に、人間が1問ずつ答える（[roles/interview.md](roles/interview.md)）。
2. AI が回答を `index.md` に記録し、深さ0の根を構成する。
   AI 自身の提案・問い返し・検討は `record.md` へ書く。
3. **根の内容を人間が承認する。** 内容が未承認のまま分割へ進まない
   （[roles/review.md](roles/review.md)）。

### 2. 根を課題へ分割する

1. AI が根の目的を達成するために解くべき課題を提案する
   （[roles/split.md](roles/split.md)）。**提案は `record.md` に書く。**
2. 課題同士の seam、親に残す前提、受け入れ条件の割り当て、子ごとの振り分けを書く。
3. 別実装の AI が前検査する（[roles/precheck.md](roles/precheck.md)）。
   指摘も `record.md` へ追記する。
4. **人間が分割を承認する。** 承認と同時に、決定した構成（子・seam・親に残すもの・
   受け入れ条件の割り当て）を根の `index.md` へ昇格させ、証跡を `record.md` に残す。
   承認後だけ深さ1の課題ノードを作る（[roles/review.md](roles/review.md)）。

### 3. 各課題で解決法を決める

1. 課題ごとに別チャットを cold start する。
2. 課題ノードと祖先の閉包だけを読み、その課題に対する解決法を決める。
3. **解決法の決定内容を人間が承認する。**
4. AI が承認済みの決定を、深さ2の解決法ノードへ分割提案する。
5. 別実装の AI による前検査後、**人間が分割を承認する。**

### 4. 各解決法をシステムへ落とし込む

1. 解決法ごとに別チャットを cold start する。
2. 親（課題ノード）の決定を詳細化し、それに伴う機能を決める。選び直さない。
3. **詳細化と機能の決定内容を人間が承認する。**
4. AI が承認済みの決定を、深さ3のシステムノードへ分割提案する。
5. 別実装の AI による前検査後、**人間が分割を承認する。**

### 5. 深さ3を実装へ渡す

深さ3は設計ツリーの葉であり、それ以上分割しない。各システムの内容と受け入れ条件を
人間が承認したあと、将来の実装者（implement）へ渡す。

**実装者へ渡すのは閉包の設計書（`index.md`）だけである。**記録は渡さない。
記録を読まないと実装できないなら、設計書が不足している。

## 承認の原則

**承認の目的は、最終的にシンプルで読みやすい設計書にすることである。**（2026-09-03 人間の決定）

承認は手続きの通過儀礼ではない。承認を重ねた結果ツリーが読みにくくなっているなら、
その承認列は目的を果たしていない。以下の規則はすべてこの目的に従属する。

具体化の第一歩として、**設計書と記録を分ける**（2026-09-03 人間の決定）。
承認は、記録から設計書へ内容を昇格させる唯一の門であり、承認のたびに設計書へ
足されるのは決定だけになる。経緯・指摘・却下案は記録に積まれ、設計書は太らない。
規則は [設計書と記録を分ける](#設計書と記録を分ける)。

何をもって「読みやすい」と判定するかの基準（分量の上限など）は引き続き検討中。

人間の承認は2種類あり、片方で他方を代用しない。

1. **決定の承認**: そのノードに書かれた目的、課題への解決法、システム化の内容を確定する。
2. **分割の承認**: その決定を、提案された子ノードと seam に分けてよいと確定する。

深さ3は子を作らないため、決定の承認だけを行う。

**提案するのは AI、確認するのは別実装の AI、承認するのは人間**（2026-08-25 決定）。
演者を役割で固定する。提案した側は承認できない、という原則の現時点での具体形である。

3 は人間の前に置く前検査であり、拒否権は持たない。指摘を付けて人間へ渡すだけで、
承認するかは人間が決める。**確認する AI は、提案した AI と別実装であること**
（同じモデルだと同じ見落としをする）。

分割条件と受け入れ条件の案は AI が作るが、決定と分割は毎回人間が承認する。
人間は個別承認に加えて、[criteria/precedents.md](criteria/precedents.md) で判断基準自体を
後から覆せる。

## 子の振り分けは親が書く

分割が承認されたら、子ノードを作るのは親であり、**各子の `index.md` の
`## 親からの振り分け` は親が書く**。子はこの節を書き換えない。

- 責任（1文）
- 詳細化の対象（親の決定のどの部分を詳細化するのか）
- 継承する制約（祖先から降りてくる制約・不変条件）
- 割り当てられた受け入れ条件
- `uses_seams`
- 親の決定の版参照（`<node-id>@<日付>-<種別>-<連番>`）

転記が済んで初めて `children-created`。ここが空のまま子チャットを開くと、子は親の
提案本文を読み直して自分の担当を再解釈することになり、**開くたびに結論が変わる。**

振り分けが間違っていると子が判断した場合、子は自分で直さず `boundary_request` を返す。

## 子は別チャットで話す

分割が承認された時点で、親のチャットは終わる。子ごとに新しいチャットを開く。

- 1チャットの文脈が1ノードに閉じるので、深い木でも文脈が飽和しない
- **子チャットは cold start する。**会話の続きではなく、ファイルだけで始まる
- 親を再開するとき（boundary_request の受理など）も、旧チャットを続けずに cold start する。
  続けると、チャット内にしかない情報がまた生まれる

別チャットにしても、**兄弟不可視性は担保されない**。同じワークスペースのファイルを読める
ため、規約として禁止しているだけである（読もうと思えば読める）。担保が必要になったら、
閉包だけを複製した隔離ディレクトリを渡す方式に変える。

子チャットに渡すのはこれだけ。

```
harness/README.md に従って <ノードのパス> を進めてください。
閉包（自ノードと祖先チェーンの index.md）を先に読んでください。
記録（record.md）は読まなくて構いません。
```

これで始められないなら、その原因は**ツリーに書かれていない情報が親のチャットに
残っていた**ことであり、直すべきはチャットではなくツリーである。
受け入れ条件「再現」は、毎回ここで検査されることになる。

**閉包は設計書だけである。**祖先の `record.md` は読まない。読まないと進めないなら、
それは設計書に昇格し損ねた決定があるということで、記録を読んで回避してはいけない。
その決定を持つノードへ `boundary_request` を返すか、そのノードを再開して昇格させる。
記録を開いてよいのは、前検査・承認・「なぜそう決めたか」を追うときだけ。

## 子から親・祖先へ戻す（boundary_requests）

別チャットになると、子が親へ口頭で相談する経路が無くなる。
不変条件「子は親を書き換えない」に、次の例外を1つだけ置く。

**子孫は、まず修正が必要な直近の親または境界所有者の `record.md` の
`## boundary_requests` に追記する。**起票した子は祖先の設計書を直接書き換えない。
対象ノードを別チャットで cold start し、そのノードの担当として設計書を修正する。

起票は記録側にしか置かない。設計書に載るのは、受理された結果（新しい制約・seam）だけである。

```md
## boundary_requests

- from: <起票したノードの id> / date: <日付>
  対象: <動かしたい seam / owns / 責任範囲>
  理由: <観測した事実と、現状では決められない理由>
  status: open        # open / accepted / rejected
```

親のチャットは終わっているので、これは**親を再開する起票**になる。親を直すだけでは
祖先の目的・制約・seam と整合しない場合は、親からさらにその祖先へ `boundary_request` を
起票する。必要な最上位の祖先から人間の承認を取り直し、その後に下位へ決定を降ろす。

`open` の起票には次の制限がある。**兄弟情報の迂回路になるため。**

- 書けるのは境界・観測事実・要求だけ。起票元の内部設計を書かない
- `open` は非権威的。他の子はこれを祖先の決定として読んではいけない。継承もしない
- 親が受理し、**親の `index.md` へ昇格して正式な seam になって初めて**、子へ降りる。
  記録に `accepted` と書いただけでは降りない

親または祖先の修正も通常の**決定の承認**を必要とする。修正によって子の構成が変わる場合は、
**分割の承認**も取り直す。受理して境界を直したときの失効範囲は、変更の種類で決まる。

| 変わったもの | 失効するもの |
| --- | --- |
| seam | **その seam の両端**（受信側と送信側）の子と、その子孫 |
| 責任範囲 / owns / 受け入れ条件の割り当て / 書き込み権限 | 対象の子と、その子孫すべて |

seam ID で追えるのは1つ目だけである。2つ目は名指しの仕組みが無いので、部分木ごと失効させる。

**1つ目が「両端」なのは、`uses_seams` が受信側しか列挙しないため。**送り手はその seam を
名指ししていないので、受信側だけを失効させると送り手に変更が届かない。
列挙の仕組みは変えず、失効の判定だけを両端へ広げる
（`root@2026-08-31-decision-4`。前検査が `s2` の送り手 `authoring`、`s6` の送り手 `change` に
失効が届かないことを検出した）。

## 予算

提案側のハード上限。超える提案はしてはいけない（分割を諦めるか、切り方を変える）。

| 項目 | 既定 |
| --- | --- |
| 最大深さ | 3 |
| 1ノードあたりの最大子数 | 5 |

## 既存ノードの移行

設計書と記録の分離（2026-09-03）より前に作ったノードは、`index.md` 1枚に両方が
入っている。**一括では直さない。そのノードを次に開いたチャットで、最初に分離する。**

1. `record.md` を [record-template.md](record-template.md) の形で作る。
2. 分割提案・前検査・承認証跡・`boundary_requests`・`seam_inbox`・AI の blockquote を、
   `index.md` から `record.md` へ**そのまま移す**（要約しない）。
3. 承認済みの分割提案が持っていた構成（子・seam・親に残すもの・受け入れ条件の割り当て）を、
   `index.md` の `## 構成` へ昇格させる。**移行で決定内容を変えない。**
4. 本文に残った履歴の痕跡（「旧: …」「…の指摘で改訂」）を版参照に置き換える。
5. 分離後の `index.md` を人間が一読する。

移行は決定内容を変えないので、**決定の再承認は要さない**。ただし 5 は省かない。
読みやすい設計書にすることが目的であり、読まずに分離しても目的は確認できない。

分離の途中でも、ツリーは壊れない。分離済みのノードと未分離のノードが混在してよい。
未分離のノードでは、`index.md` の記録相当の節が `record.md` の代わりになる。

**1点だけ、決定の修正にあたるものがある。**`## boundary_requests` と `## seam_inbox` の
置き場は `root@2026-08-31-decision-3` が「根の `index.md`」と決めた。この分離は置き場を
`record.md` へ移すので、根の決定の修正として人間の承認が要る。搬送路そのもの
（子孫は親のここへ追記し、親が権威化して降ろす）は変えない。変わるのは節の所在だけ。
