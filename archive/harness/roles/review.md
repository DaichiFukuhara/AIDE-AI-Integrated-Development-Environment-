# 役割: 人間レビュー（review）

各ノードの**決定**と、深さ0-2のノードの**分割**を人間が承認または却下する。
提案した AI と前検査した AI は承認できない。

## 0. 承認は「記録から設計書への昇格」である

承認の目的は、最終的にシンプルで読みやすい設計書にすることである
（2026-09-03 人間の決定。`harness/README.md`「承認の原則」）。

提案・指摘・対話は `record.md` に積まれている。**承認したものだけを `index.md` へ移す。**
承認と昇格は同じ場で行い、「記録側だけ承認済み」の状態を残さない。
昇格させないまま `approved` と書いた決定は、子にも実装にも降りない。

昇格のときに設計書へ持ち込まないもの: 却下・取り下げた案、前検査の指摘、
他の切り方との比較、承認の経緯。これらは記録に残り、版参照で引ける。

## 1. 決定の承認

### 入力

- 対象ノードの `index.md`（設計書）と `record.md`（記録）
- 祖先チェーンの `index.md`
- `harness/` 一式
- `harness/criteria/precedents.md`

### 確認すること

- 7項目が埋まり、現在有効な決定が一意に読める
- **設計書が設計書として読める**（記録が混ざっていない。履歴の痕跡・AI の発言・
  却下された案が本文に残っていない）
- 深さに対応する対象を決めている
  - 深さ0: ペイン・目的・利用者・成功条件・不変条件
  - 深さ1: 課題の範囲と、それに対する解決法
  - 深さ2: 親の決定の詳細化と、それに伴う機能
  - 深さ3: 実装するシステムの境界・振る舞い・受け入れ条件
- 受け入れ条件を人間が理解し、達成を判断できる
- 祖先の目的・制約・seam と矛盾しない
- 仮置きと、実装へ任せる判断が明示されている

承認したら、版参照・承認者・日時・承認種別 `decision` を **`record.md` の
`## 承認証跡`** に記録し、`index.md` の `status: decision-approved` と
`decision_ref: <版参照>` を更新する。

## 2. 分割の承認

深さ0-2だけで行う。対象ノードの決定が承認済みで、別実装 AI の前検査を通った提案を読む。

人間は前検査の判定に拘束されない。ただし重大指摘を残したまま承認する場合は、
その理由を承認証跡へ書く。

分割の承認では、次も確認する。

- **子ごとの振り分け**が全ての子について書かれている（責任 / 詳細化の対象 /
  継承する制約 / 割り当てられた受け入れ条件 / `uses_seams` / 親の決定の版参照）
- 子が1つであることを理由に却下しない。深さ0-2は子が1つでも分割する
- 各子が、次の深さの意味に合っている

承認したら、次の順で行う。

1. 版参照・承認者・日時・承認種別 `split`・対象の分割提案 id を
   `record.md` の `## 承認証跡` に記録する。重大指摘を残したなら、その理由も。
2. **提案の内容を親の `index.md` の `## 構成` へ昇格させる**
   （子・seam・親に残すもの・受け入れ条件の割り当て）。ここが子の閉包になる。
   子ごとの振り分けは各子へ転記するので、親の設計書には残さない。
   `seams` と `split_ref` を frontmatter に反映し、`status: split-approved` とする。
3. その後でだけ子ノードを作る。

子を作るときは、**親が振り分けを子の `index.md` の `## 親からの振り分け` へ転記する。**
転記が済んで初めて `children-created`。子はこの節を書き換えない。

提案が前検査後に編集されていたら、承認せず再度 precheck へ戻す。

## 3. 親・祖先を修正した場合

`boundary_request` により親または祖先を修正した場合、そのノードの決定承認は失効する。
内容を修正したノードから順に、必要な最上位の祖先まで決定を承認し直す。

起票は `record.md` にあるが、**受理したら結果を `index.md` へ昇格させる。**
記録に `accepted` と書いただけでは、新しい制約も seam も子へ降りない。

修正によって子の責任、seam、受け入れ条件の割り当てが変わる場合は、分割も前検査と
人間承認をやり直す。上位の決定が確定してから下位ノードを再開する。
