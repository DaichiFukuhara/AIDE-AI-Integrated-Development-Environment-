## 1. これは何を決めるものか

<!-- 深さ1: 課題の範囲と、それに対する解決法 -->

**課題**: 実装するとき、設計に無いことが実装 AI によって勝手に決まり、人間がそれを
知らないまま製品に入る。

**解決法（原理）**: **決定照合ゲート**を置く。版を固定した閉包と実装成果物を照合し、
実装の過程で追加された設計上の決定を次の4つに分類する。

| 分類 | 意味 | 行き先 |
| --- | --- | --- |
| `設計済み` | 閉包に既に書いてある | なし |
| `委任内` | 閉包の質問6が明示的に委ねた範囲に収まる | なし（記録のみ） |
| `design_gap` | 委任範囲を超えて決めた。設計に無い | `s3.gap` → authoring |
| `境界変更` | 既存の境界そのものを動かす必要がある | `s4.boundary` → change |

**委任外の決定は、人間が権威化するまで対象範囲を確定させない。**

`s6.halt` は**停止と再開の両方**を運ぶ（`root@2026-08-31-decision-4` 案）。
- **停止**: 旧閉包を凍結してから `halt_ack` を返す
- **再開**: その閉包を止めている理由がひとつも残っていないと親が判断したときに降り、
  受領確認を返して**元の閉包で**照合を再開する。新しい閉包が降りた場合は再開ではなく、
  新しい版での開始可否判定からやり直す

## 2. なぜ要るのか

設計が完全でなくても実装は進み、AI は空白を必ず埋める。埋めた事実が残らないと、
人間の知らない決定が製品に入り、後から指摘できない。
逆に v1 の strict Observe は「何を決めてよいか」を書かなかったため実装が止まり続けた
（停止病）。**監査と停止病の両方を同時に避ける**必要があり、そのために「埋めてよい範囲」と
「埋めたら起票する範囲」を分類として持つ。

## 3. 誰が使い、誰が影響を受けるか

- **使う**: 将来の実装 AI（implement 役）と、成果物をレビューする人間
- **影響を受ける**: `s3.gap` を受け取る側、`s4.boundary` を受け取る側

## 4. 終わったとどうやって分かるか（受け入れ条件）

<!-- 親からの割り当ては「監査」1つ。ただし implement 役が対象外のため、
     一部は deferred として明示する（Codex の指摘 2026-08-30） -->

- [ ] **分類の網羅**: `閉包の版参照 + 成果物の差分 + 決定記録 + 証拠位置` を入力として、
      実装で生じた設計上の決定がすべて上の4分類のいずれかに割り当たる
- [ ] **自己申告漏れの検出**: 実装 AI の申告だけに頼らず、独立した照合によって
      「未記録の決定が無いこと」を確認できる（申告漏れは検出されなければ意味がない）
- [ ] **起票の対応**: `design_gap` に分類された項目には対応する `s3.gap` の起票が、
      `境界変更` には `s4.boundary` の起票が必ず存在する
- [ ] **版の保持**: すべての実装記録が、受領した `s1.closure` の版参照を保持している
      （閉包を再構成できることは `authoring` 側の責任なので、ここには含めない）
- [ ] **停止の実効**: `s6.halt` の停止を受けたあと、**旧閉包による確定が実際に
      止まったこと**を示せる。`halt_ack` はその証明であり、単なる受領確認ではない
- [ ] **再開の実効**: `s6.halt` の再開を受けたあと、**元の閉包での照合が実際に
      再開したこと**を示せる。停止中に届いた旧版の結果を誤って採用していないことも含む
- [ ] *(deferred)* **実製品での事後指摘**: 根の「監査」が求める「実際の実装成果物に対して
      後から指摘できる」ことの検査。
      **再開条件: implement 役が作られ、最初の実装成果物が得られたとき**

> 🧭 **AI**: implement 役が不在なので、上の5条件は**模擬実装**で検査します。
> 分類・起票・停止競合はそれで検査できますが、実製品に対する事後指摘は検査できないため、
> 最後の1つだけを `deferred` として残します。ノード全体を `deferred` にはしません
> （設計と分割は進められるため）。ただしこの状態では**根の受け入れ条件「監査」を
> 満たしたとは判定しません**。（Codex の助言により 2026-08-30）

## 5. 変えてはいけない前提

すべて根から継承。このノードで選び直さない。出所は `root@2026-08-29-decision-2`（本文1〜7）と
`root@2026-08-31-decision-3`（split-4 の seam 定義・子ごとの振り分け・共通語彙）の2つで、
下の各項目のうち共通語彙・確定の定義・封筒と搬送路は decision-3 側から来ている。

1. 不変条件1〜4 と `boundary_requests` の例外
2. 正規単位はノード。共通語彙。版参照規約
3. **封筒の最小項目は全 seam について親が固定済み**（`s1` / `s6` だけではない）。
   一方 `payload` の書式は `authoring` の所有であり、`handoff` が固定してはいけない
4. seam の搬送は必ず親を経由する。兄弟のファイルに直接書かない
5. **実装役 implement は現時点で対象外**。implement が守る境界契約は設計してよいが、
   implement 自体の内部手順や役割定義を作るのはこの制約に抵触する
6. **`s6.halt` は停止と再開の両方**を運ぶ。再開を降ろすかどうかの判断は `change` 側で
   行われ、`handoff` は判断しない（`root@2026-08-31-decision-4` 案）
7. 予算（深さ3・子数5）、ツール固有機能に依存しないこと

## 6. 決めないこと・任せること

<!-- 「実装言語・フレームワークは自由」は広すぎる。フレームワークは境界・依存・安全性・
     運用を変え得る（Codex の指摘 2026-08-30）。規則の形で書く -->

### 委任してよいものの規則（3条件をすべて満たすもの）

1. 閉包で明示的に禁止・指定されていない
2. 外部挙動・seam・受け入れ条件・永続データ・安全性・運用境界を変えない
3. 対象ノードの内部に閉じ、局所的に差し替えられる

3つを満たさないものは `design_gap` であり、実装 AI が黙って決めてよいものではない。

**各設計ノードの質問6に書かれた範囲が優先。暗黙の委任は認めない。**

### 担当外（他ノードの責任）

- 各設計ノードの委任範囲の**中身**（それは各ノードの質問6が決める）
- 逸脱が見つかったあとの**是正内容**

ただし、**確定を止めること**と **`s3` / `s4` へ送ること**は `handoff` の責任から外れない。

## 7. 分からないこと・仮置きしていること

- **模擬実装をどう作るか**（誰が実装役を演じ、何を成果物とするか）。深さ2で決める
- **`design_gap` の粒度**: 「実装ファイル単位」は誤り。根が正規単位をノードと決めている
  ため、**独立して承認可能な不足決定＝将来のノード単位**に寄せる、を仮置きとする。
  この寄せ方が実際に機能するかは未確認
- 「独立した照合」を人手でやるか検査器でやるか。ツール非依存だけが制約

### 親に残すもの

1. **4分類**（`設計済み` / `委任内` / `design_gap` / `境界変更`）と、その行き先
   （`s3.gap` / `s4.boundary`）。子は分類を増やさず、減らさない
2. **委任してよいものの3条件**（本文6）。子は緩めない。
   各設計ノードの質問6に書かれた範囲が優先で、暗黙の委任は認めない
3. **委任外の決定は、人間が権威化するまで対象範囲を確定させない**
4. **implement 役は対象外**。子は implement の**内部手順や役割定義を作らない**。
   作ってよいのは implement が守る**境界契約**だけ
5. **`deferred` は親が保持する**: 実製品での事後指摘（本文4の最後の条件）は
   `handoff` が持ち、子へ割り当てない。再開条件は「implement 役が作られ、
   最初の実装成果物が得られたとき」。担当がいるように見せかけない
6. **`payload` の書式は `authoring` の所有**。`handoff` の子は封筒も payload 書式も
   決めない
7. **`design_gap` の粒度は「独立して承認可能な不足決定＝将来のノード単位」**
   （仮置き。本文7）。実装ファイル単位で数えない
8. **模擬実装は `gate` が用意して `detect` へ渡す。**二重に作らせない。
   模擬実装は implement 役の代替ではなく、検査用の入力である。

   `gate` が閉包を抜粋・要約して渡すことは判定への踏み込みにあたる。

### 他の切り方との比較

- **3分割案（gate / classify / escalate）**: `escalate` は `gate` と同じ
  「外部との出入りと順序」であり、分けると `halt` の受領（gate）と `gap` の起票
  （escalate）が**同じ状態機械を2子に跨って共有**する。
  seam は**3本ではなく4本**（precheck v1 軽微3 の要求により、却下・失効経路を
  含めて再計数した）:
  - `gate` → `classify`: 判定の基準
  - `classify` → `escalate`: 分類結果
  - `escalate` → `gate`: 起票の応答（受理・却下・失効）を開始可否へ反映
  - `gate` → `escalate`: `halt` を受けたとき、進行中の起票を止める
  現案の2本に対して倍。切る位置が悪い
- **局面で切る案（実装前 / 実装中 / 実装後）**: 時間で切ると、同じ「委任範囲」を
  3子が別々に解釈する。委任範囲は1か所で持つべき
- **分割しない案**: 深さ0-2は必ず分割する。加えて2子は**検査方法が違う**。
  `detect` は模擬実装への判定精度（申告漏れを拾えるか）で測り、
  `gate` は順序と停止の実効性（ack が揃うまで進まないか）で測る
- 子2つ、seam 2本、深さ2。予算内
