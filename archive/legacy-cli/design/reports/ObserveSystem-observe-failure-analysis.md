# ObserveSystem Observe不合格の原因分析

- 実施日: 2026-08-03
- 対象: `design/lanes/ObserveSystem.md`
- 対話量: 新規25往復、50発言以上
- Observe結果: 2回とも `fail`
- 根拠レポート: `ObserveSystem-1.md`、`ObserveSystem-2.md`

## 結論

不合格が続く主因は設計方針の不足ではなく、現在のstrict観察者が要求する「分割可能性」の粒度が、この段階の横断的な機能設計に対して過剰なためです。

現在の観察者は、単に実装方針と受け入れ条件が決まっているだけではpassにしません。「対象レーンだけを読めば、既存コードを調べず、複数コンポーネント間の入出力まで確定した状態で実装できること」を要求しています。ObserveSystemはCLI、観察レポート、accept、status、pool、VS Codeを横断するため、この基準では接続先を一つ決めるたびに、さらに詳細な関数、フィールド、責務境界の定義が要求されます。

## 実際のObserve結果

### 1回目

次の4点が未決定として不合格になりました。

1. `resolveObserveLevel` の返り値型
2. `light` 時の `separability.ok` の表現
3. `--force` とstaleの関係
4. 重複宣言のエラー条件

これらは一度に既定値を決め、レーンへ最終決定として追記しました。

### 2回目

上記4点をすべて確定しても、次の詳細が未定義として再び不合格になりました。

- `observeLevel` を既存レポートのどこへ格納するか
- poolへ記録するフィールド名と更新責務
- レーンハッシュとstale判定APIへの接続方法
- accept、status、VS Codeが共有するデータ構造
- `--force`が迂回する検査と迂回しない検査の境界
- 観察者レスポンスの検証主体とエラー契約

これは設計の目的・挙動・安全境界ではなく、既存実装へ落とし込む際の内部インターフェース設計です。

## なぜ会話を進めても収束しにくいか

### 1. strictの合格条件が「単独実装可能」だから

観察者プロンプトは、他への依存がインターフェースとして明示され、セクション単独で実装単位として成立することを要求します。横断機能では、既存コンポーネントとの接続をすべて書かない限り分割可能性NGになりやすい基準です。

### 2. 対話AIに「設計完了」の停止条件がないから

`mdtalk` は新しい文章が追加されるたび、曖昧点、例外、別視点を探して質問します。「目的、受け入れ条件、安全境界が決まれば終了」「残りは実装時判断としてよい」という完了条件がないため、回答するほど次の細部が生成されます。

### 3. 会話ログ全体を観察対象にしているから

レーンには確定事項だけでなく、途中の質問、候補、未解決と書かれた過去の注釈も残ります。最後に決定を追記しても、観察者はログ全体から追加の未確定表現を探せます。確定仕様と検討履歴が分離されていません。

### 4. ObserveSystem自身が改善前のstrict基準で審査されるから

このレーンは「分割可能性チェックをlightではスキップする」改善を設計しています。しかし機能が未実装なので、このレーン自身には現行strict基準しか適用できません。改善機能を作るための設計が、改善前の過剰な基準で止められるブートストラップ問題です。

## そこまで細かく設計する必要があるか

今回の段階では必須ではありません。

次はすでに決まっています。

- `observe-level: light|strict`
- 未指定は `strict`
- `light` は分割可能性だけをスキップする
- 矛盾検出、ハッシュ、stale検査は維持する
- 未知値や重複宣言はエラーにする
- レベルをレポート、status、accept、VS Codeへ伝播する
- 既存データは `strict` と解釈して互換性を保つ
- 単体・結合・VS Codeテストの主要条件

同一リポジトリ内の内部関数名、JSONフィールドの正確な配置、更新責務の細部は、実装時に既存コードを確認して決めても手戻りが限定的です。外部公開API、他チームとの契約、データ移行を伴う境界なら事前確定の価値がありますが、今回はstrict観察者がそれらと同じ粒度を一律に要求しています。

## 推奨する改善

1. `light` では矛盾だけを合否条件にし、分割可能性の指摘は助言またはスキップにする。
2. レーンに「最終仕様」セクションを設け、Observeは会話ログよりそのセクションを優先して判定する。
3. `mdtalk` に完了条件を与え、受け入れ条件と安全境界が確定した後は新しい質問を増やさず、未解決点を「実装時判断」へ分類できるようにする。
4. strictは外部インターフェース、高リスク、複数チーム間契約があるレーンに限定する。
5. ObserveSystemの初回実装だけは、ブートストラップ措置として分割可能性NGを非ブロッキングにする。

## 最終判断

今回の不合格は「設計がまだ浅い」というより、「観察者の完了定義が実装詳細まで要求し、横断機能に対して収束しにくい」ことが原因です。追加の長い会話ではなく、観察レベルと完了判定の設計を緩和するのが適切です。
