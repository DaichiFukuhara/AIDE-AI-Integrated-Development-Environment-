# AIDE改修案 — 小さく試し、根拠から設計を更新する

- 作成日: 2026-09-15
- 状態: 検討用の提案。採用・承認・実装済みを意味しない。
- 対象: 作業ツリー上の `harness/` を中心に、既存CLI・MCPとの接続まで。

## 結論

最優先は、**目的・制約・委任範囲を確認したら、小さく実装して検証できる経路を作ること**。
その結果を使って現在の設計を更新する。詳細化と分割は、必要になった部分へ適用する。

人間が意図と現状を理解できるというAIDEの目的は維持する。人間に技術方式を逐一選ばせる代わりに、AIが比較結果と推奨を示し、人間が実物と根拠で判断できるようにする。

## 2. 優先する改修

### P0-1. 実装・検証まで進める最小の経路

入口では、次の内容を既存の依頼・設計からAIが埋め、不足する目的や制約だけを人間に聞く。

1. 今回確かめる未確認事項を一つ。
2. 判断に必要な最小の動作と、今回扱わない範囲。
3. 比較対象・確認方法・成功条件。
4. 作業範囲と、時間・費用など必要な上限。
5. AIに任せる判断と、人間へ戻す条件。

合意済みの依頼がこれらを満たしていれば、形式のために再承認を求めない。試作は任意の深さから開始できる。入力から結果まで必要な最小経路を作り、接続確認だけが目的なら画面は作らない。

進行は「目的と範囲の確認 → 最小実装 → 比較・実使用 → 続行／変更／終了 → 現在の設計を更新」とする。採用後の品質整備も作業範囲に含むかを明示し、試作品がそのまま本番完成扱いになることを防ぐ。

変更先: `harness/README.md`、`roles/interview.md`、`node-template.md`。実装・検証の手順を `roles/implement.md` として追加する案。

### P0-2. 承認済みの委任を、設計更新にも有効にする

現在の「決めないこと・任せること」を、実装の細部に加えて方式の比較と採用中の方法の更新にも使えるようにする。

| 判断 | 提案する扱い |
| --- | --- |
| 合意内の方式比較、局所修正、再実験 | AIが進め、根拠と結果を記録 |
| 委任範囲内の現在の方法の変更 | AIが設計と実装を更新。元の委任への参照を残す |
| 目的・守る条件・予算・委任範囲の変更 | 必要な調査と具体案を用意して人間へ戻す |
| 共通の入出力契約の変更 | 両端の影響を確認。契約変更まで委任されていれば範囲内で進め、外なら確認 |
| 公開・送信・削除等の外部影響 | 当該行為に対する既存の許可と影響範囲に従う |

人間の承認、委任に基づくAIの更新、実験による裏付けを別々に記録する。AIが自分の案を「人間承認済み」に書き換えることはしない。

`index.md` は「守る条件」「現在の方法」「未検証事項」を区別する。現在採用していても未検証の部分は明示する。仮説・観測・採用理由は `record.md` に残し、仮説を検証済み仕様として扱わない。

承認を求める際の提示は「動く結果／変更点／比較結果／限界／推奨／人間に必要な判断」に絞る。技術選択の候補一覧だけで判断を戻さない。

変更先: `roles/review.md`、`roles/interview.md`、`node-template.md`、`record-template.md`。READMEの「人間の承認だけが昇格の門」という規則も同時に整合させる必要がある。

### P0-3. 深さではなく、作業の独立性で分割する

目的・課題・方式・振る舞いという思考上の区別は残し、必ず四階層のファイルにする要件を外す。ひとつのノードに必要な説明が揃えば実装へ進める。

分割する条件は、責任と入出力を分けられ、別々に変更・検証する利益があること。常に一緒に調整する部分はまとめる。子が一つという理由だけで階層を増やさない。

兄弟の参照を許し、書き換える範囲を明示する。通常の作業は一つの担当範囲で進め、複数範囲を跨ぐ変更は調整担当がまとめる。別チャットは並行作業・独立レビュー・文脈整理に必要なときに使う。

読む権限を広げても、兄弟の内部実装へ依存してよいという意味にはしない。依存する入出力は契約として明記する。

変更先: `harness/README.md`、`roles/split.md`、`roles/precheck.md`、`roles/review.md`、テンプレートの深さに関する規則。

### P1-1. 現行仕様を短く保ち、機械で確認できる記録は機械に任せる

既存の `index.md` / `record.md` 分離を使い、別の現行仕様コピーを追加しない。重要な判断理由は記録へ一度書き、設計から参照する。

最初の自動化は読み取り専用の整合チェックとする。

- ID・親子参照・版参照が実在するか。
- 共通の入出力契約に、送り手と受け手があるか。
- 現在の版が、対応する承認または有効な委任による更新に結び付くか。
- 参照先が変わり、再確認が必要な箇所はどこか。

内容が正しいかの判定を、リンクが存在することやハッシュ一致で代用しない。初版は不整合の場所と理由を出すだけにし、文書の自動修復は後続の検証対象にする。

旧ノードは再開時に移行する現行方針を使う。出力には対応形式と読み取れなかった箇所を表示し、旧形式を黙って空の設計と扱わない。

### P1-2. レビューとMCPの停止理由を具体化する

独立レビューは、共通契約の変更、重要な不変条件、採用する方式の節目へ重点を置く。実行条件を満たす局所変更は関連テストで確認する。別モデル利用の効果は今後の検証対象であり、ログから確認できたのは独立レビューの有効性まで。

指摘は「何が起きるか」「再現条件」「影響」「先に直す必要があるか」で説明する。軽い表記修正と、実行時の破損や承認対象を特定できない問題を同じ重さにしない。

MCPには次の二段階の改修が必要になる。

1. **ツリー形式を正しく読む。** 現行のレーン形式とは明示的に区別し、現在の設計・祖先の制約・記録への参照を返す。未承認の案や過去の記録を現行仕様として返さない。
2. **検索と実行可否を分ける。** 見出し検索の結果、仕様の出所、実行の委任範囲を別に返す。検索が弱ければ、参照指定や本文の再確認で解消を試す。未解決のまま影響する実装へ進める扱いにはしない。

たとえば「実験実装を許可された範囲内で方法を比較する」は、方法の完成仕様がまだなくても、実験の目的・制約・委任を根拠に進められる。一方、仕様が見つからないこと自体を実装許可の根拠にはしない。

試作のために既存の `stopRequired` を一律にfalseにしたり、`--force` で迂回したりする方式にはしない。既存クライアントの停止契約を保ち、新しい判定情報と利用手順を揃えて導入する。MCPが通常の編集ツールを強制的に制御できない限界も残る。

変更先: `mcp.js` の `isReadableDesignFile` / `buildDesignIndex` / `toolCheckDesign`、`test/mcp.test.js`。CLI・拡張の表示は新しい情報形式が固まってから接続する。

## 3. 最初に試す一回

新しい仕組み自体も、小さな試行で確かめる。初回は既存プロジェクトの一つの体験改善を対象に、`index.md` と `record.md` の一組で回す案がよい。

ログに即した候補は、13kgameの操作感の一点。ただし、9/13時点の問題が現在も残っているとは仮定せず、対象を選ぶときに現状を確認する。

| 項目 | 試行の例。数値・対象は未採用 |
| --- | --- |
| 仮説 | 攻撃が出るまでの待ち時間を変えると、操作の意図が伝わりやすくなる |
| 最小成果 | 現状と変更案を切り替えて同じ短い場面で試せる |
| 範囲 | 操作感の当該一点。関連する設計・実装・検証まで |
| 上限 | 作業60分、追加費用なし、候補は現状を含め最大3つ |
| AIの担当 | 候補作成、入力と表示の時間の計測、関連回帰確認、推奨 |
| 人間の担当 | 実際に触ったときの理解・操作感の判断 |
| 判断 | 改善を確認できれば委任範囲内で採用・設計更新。不明なら現状維持と次に必要な確認を記録 |
| 戻る条件 | 合意済みの難易度・ルール変更が必要、または予算超過 |

これは例示であり、ゲーム改修や60分の作業を今回開始する指示ではない。計測した応答時間だけで「楽しくなった」と結論せず、人の評価と区別する。

### 試行で測るもの

- 最初に触れる成果ができるまでの時間。
- 承認・確認で作業を中断した回数と理由、人間が判断に使った時間。
- 文書の更新箇所数と、転記漏れによる再修正。
- 意図からの逸脱、関連する回帰、破棄・やり直しの量。
- 別の作業開始時に、現在の設計だけで目的・制約・現在の方法・未確認事項を説明できるか。

初回の合格条件は、必須分割なしで試作できること、委任済みの選択で再承認が発生しないこと、結果と限界から次の行動を説明できること、合意した境界を守ること。失敗した仮説を捨てられた場合も、試行としては有効な結果とする。

まずこの一回で運用が成立するかを見る。その後、規模を揃えた複数の小課題で従来手順と比べる。同じ課題の二度目が速いというだけでは学習効果と分離できないため、単純な再実施を改善の証明にしない。

## 4. 改修の順序

1. **最小試行の規約とテンプレートを用意する。** 実験・委任・任意深度の三点を一緒に扱い、既存規約との適用範囲を明記する。
2. **一つの小課題で実装・検証・設計更新まで通す。** 中断と記録負担の原因を残す。
3. **繰り返し発生した転記確認を自動化する。** 読み取り専用チェックから始める。
4. **ツリー読取と委任判断をMCPへ接続する。** 旧形式の互換性、下書きの誤昇格防止、範囲外・古い委任の扱いをテストする。
5. **有効だった手順を標準化する。** 既存の設計ツリーは段階移行する。

現時点で優先するのはP0の三点。UI拡張や大きな状態管理基盤は、試行で必要性が確認できてから具体化する。
