# AIDE v2 設計レビュー

## レビュー対象

- `design/master.md` の Observe レベル設計
- `docs/design/aide-orchestration.md` のオーケストレーション設計
- `docs/design/lane-proposals.md` の人間承認付きレーン分割設計
- `docs/design/multi-model-roles.md` の mdtalk マルチモデル設計

このレビューでは、文書間の整合性、判定規則の一意性、監査可能性、失敗時の安全性、
受け入れ条件の検証可能性を確認した。実装が現在の設計どおりかどうかは補助的に参照したが、
本書は実装完了判定ではなく設計レビューの記録である。

## 結論

**条件付き承認**とする。レーンをファイル所有権で分離し、人間だけが accept / integrate を
確定できる基本構造は一貫している。`strict` を既定にして既存挙動を維持しながら、`light` が
緩和する対象を分割可能性だけに限定する方針も妥当である。

ただし、以下の「承認前に解消する項目」は、同じ観察結果から異なる verdict を導ける、または
レポート改変を見逃す余地がある。実装の正を一意にするため、v2 の仕様確定前に文言と
受け入れ条件を更新する必要がある。

## 承認前に解消する項目

### 1. verdict の規則をレベル別に明記する

マスター設計のレベル定義では `strict` が矛盾検出と分割可能性の両方を必須としている一方、
レポート形式では verdict を矛盾検出だけで決めると読める。このままでは、矛盾がなく
`separability.ok: false` の strict レポートを pass と fail のどちらにも解釈できる。

仕様を次で固定する。

| level | pass 条件 |
| --- | --- |
| `strict` | `conflicts.length === 0 && separability.checked === true && separability.ok === true` |
| `light` | `conflicts.length === 0 && separability.checked === false && separability.ok === null` |

モデルが返した `verdict` をそのまま信頼せず、AIDE が構造化フィールドから再計算する。
再計算値とモデル値が異なる場合は、再計算値を保存すると同時に診断情報をレポートへ残す。

### 2. 矛盾フィールド名を `conflicts` に統一する

設計文書には `contradictions`、観察者の JSON インターフェースには `conflicts` が現れる。
必須フィールドの名称が揺れると、モデルが検査を省略したのか、単に別名で返したのかを
判別できない。v2 の canonical schema は `conflicts` とし、必須の配列として定義する。

各要素は最低限、次の形とする。

```json
{
  "with": "design/master.md または lanes/<topic>.md の見出し",
  "detail": "衝突している前提またはインターフェース"
}
```

空配列は「検査済みで矛盾なし」を意味する。フィールド欠落、配列以外、要素の必須キー欠落は
pass に補正せず、観察自体を失敗させる。

### 3. accept 時のレポート改変検知を具体化する

レーン本文のハッシュだけでは、観察後にレポートの `observeLevel` や `verdict` を直接編集した
ケースを検知できない。「現在のヘッダとの突き合わせ」に加えて、レポートの完全性を守る
規則が必要である。

v2 では次のいずれかを選び、受け入れ条件に含める。

1. レポート作成時に、canonical metadata と構造化結果から `reportHash` を生成し、accept 時に
   再計算する。
2. 構造化結果を改変しにくい別 state に保存し、Markdown レポートを表示専用の投影とする。

少なくとも accept は、現在の解決済みレベル、レポートの `observeLevel`、レーンハッシュ、
再計算した verdict の4点を照合する。`--force` が迂回できる検査も一覧で明記し、未判断の
分割提案や壊れた設定まで迂回しない現在の原則を維持する。

### 4. 「先頭の第一プロトコルヘッダ」の境界を定義する

「レーン先頭」が BOM、空行、Markdown 見出し、別の HTML コメントを許すかが未定義である。
パーサーごとの解釈差を避けるため、次の文法に固定する。

- UTF-8 BOM と空行は先頭判定で無視してよい。
- 最初の非空要素が `<!-- mdtalk protocol` ブロックなら、そのブロックだけを読む。
- Markdown 本文の開始後に現れる protocol ブロックは設定として扱わない。
- protocol ブロックが閉じていない場合は既定値へ黙ってフォールバックせず、設定エラーにする。
- 重複検査の範囲は、採用した第一 protocol ブロック内に限定する。

## v2 確定時に追加する受け入れ条件

- [ ] strict で矛盾なし・分割可能性 NG の応答が必ず fail になる。
- [ ] light でモデルが `separability.ok: true` を返しても、契約違反として検知できる。
- [ ] `conflicts` 欠落、不正な要素、モデル verdict と再計算値の不一致を個別に検証する。
- [ ] レポートの `verdict` または `observeLevel` を手編集すると通常 accept が拒否される。
- [ ] `--force` が迂回する検査と、迂回しない検査をそれぞれ結合テストで固定する。
- [ ] BOM、先頭空行、本文中の偽 protocol、未閉鎖コメントをパーサーの単体テストに含める。
- [ ] 旧レポートを `strict` とみなす際も、当時のレポート形式で検証可能な項目は再検証する。

## 非ブロッキングの改善提案

### 設計書の版と実装フェーズを分離する

オーケストレーション文書には「第一版」「v1 実装メモ」「Phase 4 実装済み」が同居している。
設計バージョン、製品バージョン、実装進捗を別のメタデータにすると、v2 が何を指すかを
誤解しにくい。文書冒頭に `designVersion`、`productVersion`、`status`、`lastReviewed` を置く。

### エラーコードを列挙する

「他の Observe エラーと区別できる終了コード」だけでなく、設定不正、バックエンド失敗、
応答スキーマ不正、判定 fail を数値と意味の表で定義する。CLI、VS Code、将来の自動化が
標準エラーの日本語文面を解析せずに分岐できるようになる。

### status の stale 理由を機械可読にする

単一の真偽値だけでなく、`lane_hash_changed`、`observe_level_changed`、
`report_integrity_failed` のような理由コードの配列を返す。人間向け表示は理由コードから
生成し、CLI と VS Code の説明がずれないようにする。

## 確認済みの強み

- ファイル単位の所有権により、異種 AI の同時書き込み衝突を構造的に避けている。
- observe、accept、integrate を分離し、重い統合処理と人間の軽い承認操作を分けている。
- `light` でも矛盾検出と stale 検査を残し、緩和範囲を限定している。
- 未判断のレーン分割提案を `--force` でも迂回させず、レーン構造の決定権を人間に残している。
- 旧レポートの既定を `strict` とするため、移行時に安全側へ倒れる。
- AI バックエンドをコマンド差し替え可能にし、ネットワーク不要の結合テストを設計できる。

## 再レビュー条件

上記4つのブロッキング項目がマスター設計へ反映され、追加した受け入れ条件の担当フェーズが
決まった時点で再レビューする。非ブロッキング項目は v2 リリースを止めないが、少なくとも
設計バージョンの定義はリリースノートで明示する。
