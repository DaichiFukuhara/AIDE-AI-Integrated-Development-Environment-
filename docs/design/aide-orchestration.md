# AIDE — レーン分割・並列設計オーケストレーション

> この文書は 2026-07-09 の人間×AI対話で合意したアーキテクチャの第一版。
> 「確定」= 対話で合意済み。「❓」= 未決で、今後 mdtalk の監視下で対話して詰める。

## 目的 / 背景

巨大なプロダクトを AI と設計するとき、1つの巨大チャットや1枚の巨大ファイルでは
(a) コンテキストが全履歴を引きずってトークンが爆発する、(b) 複数 AI を使うと
同一ファイルへの書き込み衝突が起きる、(c) 人間が AI の応答を待つ時間が無駄になる。

AIDE はこれを**ファイル構造で解決**する。設計対象を「考慮すべき項目」ごとの
**レーン**（独立した対話ファイル）に分割し、人間は複数レーンの対話を並列に
回遊する。各 AI は自分のレーンだけを読むためトークンコストはプロダクト全体
ではなくレーンのサイズにしかスケールしない。レーン＝ファイルで所有権を分ける
ため、Claude / Codex など**異種 AI の併用でも書き込み衝突が起きない**——
ファイルシステムそのものが調停役になる。

中心原則は2つ:

1. **衝突は防止でなく耐性で扱う**。アクセプト時点で将来の全衝突を保証するのは
   不可能。代わりに「分割可能性」（疎結合・依存のインターフェース明示）を
   アクセプトの門番にすることで、衝突が起きても影響を局所に留める。
   分割可能性を通過したセクションは単独の実装単位になり、そのまま
   spec-driven-build 等へ個別投入できる（実装フェーズの並列化保証を兼ねる）。
2. **マージボタンを持つのは常に人間**。AI は提案・検査・清書をするが、
   マスター設計書に何を入れるかの最終判断は人間のアクセプトのみ。

## 用語と役割（確定）

| 役割 | 担当 AI | 実行形態 | やること |
|---|---|---|---|
| **レーンAI** | Claude（sonnet 等） | 常駐（保存のたび） | レーン内で人間と並列対話。質問・展開・整理（= mdtalk） |
| **観察者** | Codex（外部 AI） | **ボタン式・レーン単位**（人間が任意のタイミングで起動） | ① 他レーン/マスターとの矛盾検出 ② **分割可能性の判定**（依存が明示されているか・単独で実装可能か）。**合格がアクセプトの前提条件** |
| **人間** | — | — | 対話・観察ボタン・**アクセプト**・統合指示 |
| **プール** | —（ファイル） | — | アクセプト済み・未統合の項目が溜まるステージング領域 |
| **マスターAI** | Opus / Fable | **別セッション・複数回のバッチ**（人間が起動、常駐しない） | master + pool だけを読み、**清書**して master へ反映。プール項目間の矛盾を発見したら差し戻し |

観察者を対話 AI と**別ベンダー**にするのは意図的: 会話に参加していない外部の
目だからこそ、対話の流れに引きずられずに矛盾へ気づける。

## ファイル構成（確定・詳細は❓）

```
design/
  master.md          # マスター設計書。アクセプト済みの内容だけが載る「正」。
                     #   最初に型（テンプレ）から作る。項目はエージェントが
                     #   必要に応じ自動追加できる
  pool.md            # ステージング。アクセプトされた項目が統合待ちで並ぶ
  pool-archive.md    # 統合済み項目のアーカイブ（監査証跡。消さない）
  lanes/
    <topic>.md       # レーン。人間×レーンAI の対話ファイル（mdtalk 監視対象）
  reports/
    <topic>-<n>.md   # 観察者レポート（矛盾・分割可能性の判定結果）
```

- プール項目のメタデータ: **出所レーン・アクセプト日時・観察者レポートへの参照**
  を付ける（差し戻しのため）。❓ 具体的なエントリ書式
- ❓ `design/` 直下か `.aide/` に state を持つか等、mdtalk の `.mdtalk/` との整理

## 振る舞い / データフロー（確定）

```
[master.md をテンプレから作成] ──分割──▶ [lanes/*.md 生成]
                                              │
              ┌───────────────────────────────┤
              ▼               ▼               ▼
        [レーンA対話]   [レーンB対話]   [レーンC対話]   ← 常駐・並列（mdtalk）
              │  人間が観察ボタン（レーン単位・任意のタイミング）
              ▼
    [観察者Codex: 矛盾＋分割可能性チェック] ──不合格──▶ レポートを添えて対話継続
              │合格
              ▼
      [人間がアクセプト] ──▶ [pool.md に追記]
                                  │ 溜まったら人間が統合を指示
                                  ▼
              [マスターAI: 別セッションを起動（毎回フレッシュ）]
              master.md + pool.md のみを読む（レーン対話履歴は読まない）
                                  │
                  ┌───────────────┴────────────────┐
                  ▼                                ▼
        統合成功: 清書して master 反映      プール項目間の矛盾を発見:
        pool → pool-archive へ消化          差し戻しレポート。該当項目を
                                            レーンの対話へ戻す（AI は
                                            勝手に解決しない）
```

設計上の要点:

- **アクセプトと統合の分離**。アクセプトは人間の軽い判断（連続で押せる）、
  統合は重い仕事。プールを挟むことでアクセプトのたびに master が書き換わる
  落ち着かなさを避け、統合は溜めて1回で済ませる
- **バッチ統合だから項目間の調和が取れる**。同時期にアクセプトされた複数項目を
  マスターAIが一度に見るので、観察者がレーン単位では見切れない「プール内の
  項目同士の相互作用」を最後に捕まえられる。文体の統一も1パスで済む
- **マスターAIはステートレス**。毎回まっさらなコンテキストで master + pool
  だけを読む。失敗してもやり直せる。トークン最適化の思想と一貫

## インターフェース（たたき台・❓多数）

- 観察ボタン: ❓ レーンファイル内ディレクティブ `@observe`（mdtalk 文化と
  一貫、ファイルの中で全部が起きる）か、CLI `aide observe lanes/<topic>.md` か
- アクセプト操作: ❓ 観察者レポート合格後に何をどう押すか。レポート内
  チェックボックス / レーン内 `@accept <セクション>` / CLI。マージの単位
  （機能・関数＝セクション単位を想定）とともに要検討
- 統合指示: ❓ `aide integrate`（人間のボタン。自動では走らない）
- レーン生成: ❓ master の項目からの自動生成をどこまでやるか（テンプレの型＋
  エージェントによる項目追加、までは確定）
- バックエンド接続: mdtalk の `MDTALK_CLAUDE_CMD` 方式を一般化し、役割ごとに
  コマンドを差し替え可能にする（観察者= `codex exec` 等）❓ 具体形

## 受け入れ条件（このアーキテクチャが成立している状態）

- [ ] 3レーン以上の並列対話で、各レーンAIへの送信トークンがレーンサイズに
      比例し、プロダクト全体のサイズに比例しない
- [ ] Claude レーンと Codex 観察者が同時に動いても、同一ファイルへの書き込み
      衝突が構造上起きない（所有権: レーン=レーンAI、レポート=観察者、
      master=マスターAI、pool=人間＋マスターAI）
- [ ] 観察者が不合格（分割可能性なし/矛盾あり）と判定した項目はアクセプト
      できない
- [ ] アクセプトされた項目がプールに残り、統合バッチで master に清書反映され、
      アーカイブに証跡が残る
- [ ] マスターAIがプール項目間の矛盾を検出したとき、master を汚さずに
      差し戻せる
- [ ] 人間の操作（観察・アクセプト・統合）なしに master が変化することがない

## エッジケース / エラー処理（洗い出し・❓含む）

- プールが空のまま統合指示 → 何もせず正常終了
- 差し戻された項目の再挑戦 → レーンで対話→再観察→再アクセプトの通常ループ
- 人間が master.md を直接編集 → ❓ 許すか（原則は許す＝人間の文は常に自由、
  ただし次回統合時にマスターAIが整合を確認する、が有力）
- 2つのレーンが同名の関数/概念を別意味で定義 → 観察者の矛盾検出の主対象。
  観察を挟まず両方アクセプトされた場合はマスターAI のバッチ統合が最後の網
- 観察者（Codex）が環境にない → 観察はスキップ可能だが、その場合アクセプトの
  前提条件をどうするか ❓（警告付きで人間の責任で通せる、が有力）
- レーンの肥大化 → レーン自体をさらに分割（再帰）❓ v1 では手動

## テスト方針

- 各 AI 接続はコマンド差し替え（mdtalk のモック方式の一般化）で偽装し、
  ネットワークなしでフロー全体（観察→アクセプト→プール→統合→アーカイブ）を
  結合テストできること
- 所有権の検証: 各役割が自分の所有ファイル以外を書き換えないことをテストで保証
- 実運用テスト: **AIDE 自身の設計を AIDE のワークフローで進める**
  （この文書がマスター設計書の第一号候補）

## スコープ外

- 実装コードの生成そのもの（アクセプト済みセクション → spec-driven-build 等の
  既存パイプラインに渡す。AIDE は設計書を作るところまで）
- GUI / エディタ拡張 / リアルタイム共同編集（ファイル保存ベースで完結させる）
- 観察者・マスターAIの常駐化や自動起動（ボタンは人間が押す）
- git 連携の自動化（コミットは既存の仕組みに任せる）

## v1 実装メモ（2026-07-09 実装済み・aide.js）

❓のうち実装に必要だった項目の v1 選択。異論があれば対話で変更する:

- 観察ボタン・アクセプト・統合はすべて **CLI コマンド**
  （`aide observe/accept/integrate`）。`@observe` ディレクティブ化は
  mdtalk との統合を含めて次版で検討
- アクセプトの単位: レーン全体、または `--section <見出し>` でセクション単位
- アクセプトの前提: 最新レポートが pass **かつ** 観察時とレーンのハッシュが
  一致（観察後に編集されていたら再観察を要求。`--force` で強行可）
- プールエントリ書式: `<!-- aide:entry -->` HTML コメントメタデータ
  （id/lane/section/accepted/report）+ 本文 + `<!-- aide:end -->`
- 差し戻しの扱い: pool から外し `pool-archive.md` に `status: bounced` ＋
  理由付きで記録（レーンファイルには書き込まない——レーンの所有権は
  レーンAI＋人間にあるため）。人間がレポートを見てレーンで対話を続ける
- バックエンド接続: 環境変数 `AIDE_OBSERVER_CMD`
  （既定 `codex exec --skip-git-repo-check --ephemeral --color never -`）/
  `AIDE_MASTER_CMD`（既定 `claude -p --model opus --output-format json`）。
  引数分割して spawn、プロンプトは stdin 渡し（mdtalk と同方式）。
  Windows では npm 製 CLI（.cmd）が非シェル spawn で起動できないため、
  ENOENT/EINVAL 時のみシェル経由で再試行する。応答はログ混じり出力から
  最後のトップレベル JSON を抽出してパースする（codex exec の進行ログ対策）。
  実 codex・実 claude opus での通し（observe→accept→integrate）は
  2026-07-10 に動作確認済み
- 観察者のコンテキスト: master 全文＋対象レーン全文＋**他レーンは見出しのみ**
  （トークン最適化）

## 実装フェーズ（提案）

1. **Phase 1 — ファイル規約と手動運用**: `design/` 構成・pool 書式・master
   テンプレを決め、レーンは既存 mdtalk で監視。観察・統合は人間が手で AI に
   依頼して回してみる（規約の実地検証）
2. **Phase 2 — 観察者の接続**: `@observe` → codex exec 呼び出し → レポート
   生成の自動化
3. **Phase 3 — アクセプト〜統合の自動化**: アクセプト操作 → pool 追記、
   統合指示 → マスターAIセッション起動 → master 反映/差し戻し
4. **Phase 4 — レーン生成の自動化**: master からのレーン切り出し・項目の
   自動追加
