# mdtalk — MDファイル内対話ツール

## 目的 / 背景

設計書などの考え事を1つのMarkdownファイルの中で対話的に育てるためのCLIツール。
人間がエディタでファイルを書き保存すると、常駐する mdtalk がそれを検知し、
新しく書かれた部分を Claude（ヘッドレス `claude -p`）に読ませ、質問・コメント・
展開・別視点・整理の注釈ブロックを該当箇所の直下に**挿入のみ**で書き込む。
人間の書いた文章は構造的に一切変更されない。チャットUIは使わない。
主用途は設計書の作成で、完成した設計書はそのまま spec-driven-build 等の
実装パイプラインの入力になる。

## 対象ファイル

- 新規: `mdtalk.js` — 本体。**Node.js 単一ファイル・外部依存ゼロ**
  （`node:fs`, `node:path`, `node:child_process`, `node:crypto`, `node:util` のみ）
- 新規: `package.json` — `bin: {"mdtalk": "./mdtalk.js"}` と `engines.node >= 20`。
  依存は追加しない
- 新規: `README.md` — インストール（`npm link` 想定）と使い方
- 実行時生成: `.mdtalk/<対象ファイル名>.state.json` — 状態ファイル（後述）。
  対象MDと同じディレクトリ配下に作る

## インターフェース / シグネチャ

### CLI

```
mdtalk <file.md> [options]

options:
  --model <name>     claude に渡すモデル。既定: opus（例: haiku, sonnet も可）
  --once             監視せず1回だけ処理して終了（テスト・CI用）
  --interval <ms>    デバウンス時間。既定: 1500
  --max-notes <n>    1回の処理で挿入する注釈ブロックの上限。既定: 3
  --quiet            ログを警告以上のみに
  --init             ファイルが空/未存在なら設計書スケルトンを提案させて終了
```

- `<file.md>` が存在しない場合は空で作成して監視を開始する。
- Ctrl+C で state を保存して正常終了。

### Claude 呼び出し

```
claude -p --model <model> --output-format json
```

- 標準入力にプロンプト（システム相当の指示＋ファイル本文スナップショット＋
  変更点の要約）を渡す。
- 環境変数 `MDTALK_CLAUDE_CMD` が設定されていれば `claude` の代わりにその
  コマンドを使う（テストでモックに差し替えるための口。値は
  シェル経由ではなく引数分割して spawn する）。

### Claude からの応答スキーマ（これ以外は不正として扱う）

```json
{
  "insertions": [
    {
      "anchorLine": 12,
      "anchorText": "その行の先頭20文字",
      "type": "question | comment | expand | counter | structure",
      "text": "注釈本文（Markdown可・複数行可）"
    }
  ]
}
```

- `anchorLine` は送ったスナップショットの1始まり行番号。適用時は
  `anchorText` と照合し、ズレていれば近傍±5行から `anchorText` に一致する
  行を探す。見つからなければその insertion は捨ててログに残す。
- `insertions` は空配列でもよい（「言うことなし」を正当な応答とする）。

### 注釈ブロックの書式（ファイルに挿入される形）

アンカー行が属する段落（連続する非空行のかたまり）の直後に、空行を挟んで
blockquote で挿入する:

```markdown
> ❓ **AI**: この機能の対象ユーザーは誰ですか？（2026-07-08 14:32）
```

type とマーカーの対応: question=❓ / comment=💬 / expand=➕ / counter=🔀 /
structure=🧭。複数行の注釈は blockquote を継続する（各行 `> ` 始まり）。

### ファイル内ディレクティブ（人間→AIの合図）

- 行頭 `@ai:` で始まる行は AI への直接指示（例: `@ai: この節を整理して`、
  `@ai: 反論だけほしい`）。次回処理時に最優先で解釈し、処理後にその行を
  `<!-- done: 元の指示 -->` に書き換える（**唯一の例外的な人間行の変更**。
  これは指示の消費であり文章の改変ではない）。
- 人間が AI の質問に答えるときは、質問 blockquote の直下に普通に書けばよい。
  特別な記法は不要（AI は前回スナップショットとの差分で回答を認識する）。

## 振る舞い / データフロー

### 起動時

1. 対象ファイルと state を読む。state がなければ初期化（現内容をスナップ
   ショットとして保存し、初回は注釈しない — 既存文書を開いた瞬間に大量
   注釈が付くのを防ぐ）。
2. `--init` 指定時、またはファイルが空のとき: 「設計書スケルトンの提案」
   モードで claude を1回呼び、骨組み（目的/対象ファイル/インターフェース/
   振る舞い/受け入れ条件/エッジケース/テスト方針/スコープ外 — 空欄と
   ❓質問付き）を挿入する。
3. ファイル先頭にプロトコルヘッダ（HTMLコメント）がなければ挿入する。
   内容: マーカーの意味、`@ai:` の使い方、「AIは挿入のみ・人間の文は
   不変」という約束。Codex 等の別エージェントが同じファイルを開いた場合の
   作法もここに1行で書く（「このファイルを編集するAIは注釈blockquoteの
   追加のみ行うこと」）。

### 監視ループ

1. `fs.watch` で変更イベントを受け、`--interval` ms デバウンス。
   `fs.watch` が不安定な環境向けに 2 秒間隔のポーリング（mtime+size 比較）を
   フォールバックとして併走させる。
2. 変更後の内容のハッシュ(sha256)を計算し、以下なら**スキップ**:
   - state に記録された「自分が最後に書いた内容のハッシュ」と一致
     （自己ループ防止）
   - 前回処理時と同一ハッシュ（実質変更なし）
3. 前回スナップショットとの diff から「人間が新しく書いた/変えた行」を特定。
   AI 注釈ブロック（`> ❓` 等で始まる blockquote）内の変更は差分から除外する
   （人間がAIコメントを消す/直すのは自由、それに反応しない）。
4. プロンプトを組み立てて claude を呼ぶ。含めるもの:
   - 役割と規範（下記「注釈の規範」）
   - ファイル全文スナップショット（行番号付き）
   - 変更行の範囲と、未消費の `@ai:` 指示
   - 応答スキーマと `--max-notes` の上限
   - ファイルが 100KB を超える場合は、変更行の前後 120 行＋見出し一覧に
     切り詰めて送る（anchorLine はスナップショット基準のまま成立させる）
5. 応答 JSON を検証して挿入を適用:
   - 適用直前にファイルを再読込し、ハッシュが手順2の時点と異なれば
     このサイクルは破棄（人間が編集中。次のイベントでやり直す）
   - insertions を anchorText 照合で現在行にマップし、**下から上の順**で
     挿入（行番号ズレ防止）
   - 同一段落への注釈は state の「注釈済み段落フィンガープリント
     （段落テキストの正規化ハッシュ）」を見て抑制する。段落が編集されたら
     フィンガープリントが変わるので再注釈可能になる
6. 書き込み後、新しい内容のハッシュを「自分が書いた」として state に記録し、
   スナップショットを更新。1行ログ: `+2 notes (❓×1 💬×1) model=sonnet 3.2s`

### 注釈の規範（プロンプトに埋める内容の要点）

- 挿入のみ。人間の行の変更・削除・並べ替えの指示は絶対に出さない
  （structure タイプでも「こう並べ替えては？」という**提案文**を書くだけ）。
- 新しく書かれた部分にだけ反応する。全文への総評をしない。
- 1回の応答は `--max-notes` 以内。最も価値のある指摘に絞る。
- 設計書という用途を優先: 曖昧な要求→❓で具体化を迫る、暗黙の前提→💬で
  言語化、抜けている観点（エラー時・境界・非機能）→🔀/❓、書きかけの節→➕で
  たたき台を提案。
- 言うことがなければ空配列を返す（無理に注釈しない）。
- 日本語で書く。断定でなく対話の口調。

## 受け入れ条件 (Acceptance Criteria)

- [ ] 監視中に人間が段落を追記して保存すると、デバウンス後に claude が
      呼ばれ、その段落の直下に注釈 blockquote が挿入される
- [ ] 挿入前後で、注釈ブロックとプロトコルヘッダと `@ai:`→`<!-- done -->`
      変換以外の行が**バイト単位で不変**（テストで前後比較）
- [ ] AI の書き込みによる変更イベントでは claude が呼ばれない
      （ログで確認可能）
- [ ] 同一の（編集されていない）段落に2回目の注釈が付かない
- [ ] `@ai:` 行が次回処理で解釈され、処理後 `<!-- done: ... -->` になる
- [ ] 空ファイル＋`--init` で設計書スケルトン（8節構成）が挿入される
- [ ] `--once` が1サイクル処理して exit code 0 で終了する
- [ ] `claude` コマンド不在時、インストール案内を含むエラーで exit code 1
- [ ] 不正 JSON 応答時: 1回だけ「スキーマ厳守」を追記して再試行し、それでも
      不正ならそのサイクルをスキップしてログに残す（クラッシュしない）
- [ ] `MDTALK_CLAUDE_CMD` でモックに差し替えたテストが CI（ネットワーク
      なし）で通る

## エッジケース / エラー処理

- 保存連打・エディタの atomic save（rename書き込み）→ デバウンス＋
  ポーリングフォールバックで吸収。watch 対象が消えたら再アタッチを試みる
- 適用直前の再編集 → ハッシュ不一致でサイクル破棄（上記 5）
- anchorText が見つからない insertion → 個別に破棄・警告ログ（他は適用）
- 人間が注釈ブロック自体を編集/削除 → 何もしない（差分から除外）
- CRLF 混在 → 読み込み時に検出し、書き込み時は元の改行コードを維持
- 非 UTF-8 → 起動時にエラーで拒否（対象外と明言）
- ファイル 100KB 超 → 切り詰め送信（上記 4）＋初回に1度だけ警告ログ
- claude タイムアウト（既定 120s）→ サイクルスキップ・警告ログ
- 同一ファイルへの mdtalk 二重起動 → state に PID ロックを書き、検出時は
  起動拒否

## テスト方針

`node:test` を使用。ネットワーク・実 claude 不要で全テストが走ること。

- **ユニット**: diff 抽出（注釈ブロック除外含む）/ anchorText 照合と
  下→上挿入 / 段落フィンガープリント / `@ai:` 消費 / CRLF 維持
- **結合（--once ＋ モック claude）**: `MDTALK_CLAUDE_CMD` に固定 JSON を
  返すスクリプトを指定し、受け入れ条件の挿入系・不変系・不正JSON系・
  自己ループ系を検証
- **手動確認**: 実 claude で設計書を1本書いてみる（このツール自身の次期
  設計書を書くのが手頃）

## スコープ外（v0 ではやらない）

- 複数ファイルの同時監視、ディレクトリ監視
- VS Code 拡張・エディタ内 UI・Webhook
- git 連携（コミットは既存の git-haiku-delegate 等に任せる）
- 注釈への自動返信スレッド化（人間の回答に AI がさらにぶら下がるのは、
  通常の差分反応として自然に起きる範囲でよい）
- 英語 UI・i18n
- Windows ネイティブ対応（WSL は対象）
