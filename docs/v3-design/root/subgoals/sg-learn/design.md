# 最小の動作を試し、証拠で次の方法を選べる

利用者が全体設計の完成を待たず動く結果を試し、方法の採用・変更・終了を判断できる。

**なぜ必要か:** 設計だけで方法の有効性は確認できず、比較と実使用が必要。失敗した仮説にも再試行を減らす価値がある。

**今回の判断:** 一つの未確認事項を実験にし、予算内で実装・関連テスト・実使用を行う。結果と限界を根拠に採否を提案する。

## 5. 設計

一つの未確認事項を実験にし、予算内で実装・関連テスト・実使用を行う。結果と限界を根拠に採否を提案する。

### 小規模の意味
ファイル数や一つのsystemの完成度で小ささを定義しない。一つの未確認事項を判断するための最小動作とする。複数contextを通る場合も、今回通す最小の入出力契約は先に示す。
実験の対象外を明記し、未完成部分を本番相当と表示しない。成功条件は実験の最中に都合よく変更せず、変更する場合は新しい実験版として比較条件を残す。

### 正常・失敗・取消の扱い

正常時は割当条件に沿って下位を具体化する。参照・版の矛盾は影響範囲へ返す。仮説の不成立は実験結果として残し、仕様の成功へ置換しない。取消した候補は現在仕様へ反映せず、既存の有効版を維持する。

## 8. 品質条件

保存した仕様と根拠から再開でき、版の食い違いと未確認事項を説明できる。

| 性能・規模 | 初期は小規模なMarkdown運用。応答時間の保証値は今回設定せず、対象実験の予算を守る。 |
| 回復 | 候補の失敗で既存の有効版を消さず、操作IDと対象版から再開する。 |
