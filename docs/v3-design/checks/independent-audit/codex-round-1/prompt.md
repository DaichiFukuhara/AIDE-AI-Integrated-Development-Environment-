# 独立した設計監査の依頼

あなたはこの設計を起草していない監査担当です。別の主担当が作ったAIDE v3の設計を、現行v2の基準で監査してください。過去のpassや自己レビューを正しさの根拠にせず、文書を実際に読んで判断してください。読取り専用で作業し、ファイル編集・実装・テスト生成・外部送信・別エージェント起動は行わず、結果を最終回答として日本語Markdownで返してください。

## 対象

作業ディレクトリはAIDEリポジトリです。次を読んでください。

1. `harness-v2/README.md`、`harness-v2/criteria/README.md`、`harness-v2/roles/review.md`、`harness-v2/roles/orchestrate.md`、必要に応じテンプレートとdecompose/precheck規約。
2. `docs/v3-design/sources/requirements.md` と `docs/v3-design/README.md`。
3. `docs/v3-design/root/` 以下の10ノードのdesign.md/rationale.md全20文書。
4. `docs/v3-design/tree-state.md` が指す現在の3system closure manifestとhandoff、および各ノードの検査記録。閉包完全性に疑義がある箇所は `closures/inputs/` の該当snapshotも読んでください。
5. 判断に必要な場合、requirementsが参照する既存ログ。

現時点はtree_revision 18です。今回の成果はv3の設計であり、v3の実装や実使用がまだないこと自体を欠陥としてはいけません。ただし「実装できる」とする境界・状態・契約に不足や矛盾があれば指摘してください。

## ユーザーの意図

- 元の目標→小目標→アプローチ→システムの4階層を活かす。
- ドメイン駆動で責任と言葉の境界を分ける。
- 必要な枝から小規模実装・テスト・実使用へ進み、実験→修正→マスター/詳細設計へ反映する。
- 監査済み範囲の細かな変更は毎回全面監査せず、周期監査と必要時の監査にする。
- DDDを監査の判断軸にする。
- 読みにくさ、重複記録、終わらない監査、承認待ちや設計待ちで検証が進まない問題を扱う。

## 重点

責任ownerと共有契約の両端、初回の仮設計→plan→実験→adoption、current/audit baseline/意味hashの区別、取消・再試行・競合・周期監査の起点、DDDの適用範囲、4階層とdomain/context配置、設計閉包の完全性、v2で実行したとする公開・版管理・状態の整合を確認してください。

指摘は定義された条件の破れや具体的な複数解釈に基づくものに限定してください。設計者の好み、未知の実装技術の強制、将来の効果が未実証であることだけ、重大さのない表記改善をmajorにしてはいけません。設計の受入条件が実際に達成されたことと、将来達成するための設計が十分なことを区別してください。

## 出力

- 判定: pass / fail / blocked。open blocker/majorが1件でもあればfail。
- 読んだ対象と、読めなかった箇所・確認の限界。
- 指摘ごとに安定ID、severity(blocker/major/minor)、v2基準ID、該当ファイルと節または行、証拠、具体的な失敗例または複数解釈、影響、解消条件。
- 意味レビュー7観点の要約と3systemごとの判断。
- 複数の指摘が同じ原因なら統合する。指摘がない場合は根拠を示す。修正コードは作らない。

独立した監査結果は主担当がそのまま保存し、必要な修正後は別の呼出しで再監査します。
