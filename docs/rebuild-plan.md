# AIDE 再構築 — 目的・要件・開発環境

作成日: 2026-08-19 / 対象: AIDE v2（作り直し）

このドキュメントは、AIDE を作り直すにあたって
「なぜ作るのか」「何が必要か」「どういう環境で開発するか」を一度に見られるようにしたもの。
確定事項と、まだ決まっていないことを分けて書く。

---

# 1. 目的の整理

## 1.1 最上位の目的

`docs/design-philosophy.md` に明記されている2つ。ここは動かさない。

1. **プログラミングを一般化し、ドメインを持つ人が開発の主体になれること**
2. **制作者が製品を理解し、その責任を自信を持って引き受けられること**

重要なのは 2 が 1 の付帯条件ではなく、対等な目標として置かれていること。
「誰でも作れる」だけなら設計書は要らない。**作った本人が説明できる状態で作れる**
ことを求めるから、設計と承認と履歴が要る。

## 1.2 AIDE が担う役割

上の2つを達成する手段として、AIDE は次を引き受ける。

| 役割 | 内容 |
|---|---|
| 実装前に設計を固める | AI が暗黙に仕様を決めてしまう前に、自然言語で決着させる |
| 委譲の可視化 | 何を自分で決め、何を AI に委ねたかを、人間が認識できる状態に保つ |
| 分割と再統合 | 一度に考える範囲を小さくし、最後に全体の整合を取る |
| 判断の保存 | 結果だけでなく、検討した選択肢と却下理由を残す |

## 1.3 今回の作り直しの目的

現状: **4,143行**（aide.js 1,103 / mdtalk.js 1,811 / mcp.js 935 / その他 294）。

作り直しの目的は「小さくすること」ではない。**説明できる状態にすること**である。

philosophy にはこう書かれている。

> 制作者はすべての実装詳細を知る必要はないが、
> 製品がなぜ存在し、どのような機能を持つかを説明できなければならない。

いまの AIDE は、この基準を AIDE 自身が満たしていない。

- `mdtalk.js` 1,811行の相当部分がファイル監視・多重実行防止で、思想とは無関係な機構
- 議事録、章まとめ、共有知識ファイル、observe-level の2段階など、
  中核要件に含まれない機能が積み上がっている
- 結果として「AIDE の本体はどれか」が一言で言えない

したがって作り直しのゴールは、**思想と実装が1対1で対応し、
コードを指して「これがこの思想に対応する」と言える状態**にすること。
行数はその結果であって目的ではない。

## 1.4 前提として置いていること（要確認）

以下は文書と経緯からの推測。違っていたら指摘してほしい。

- これは**研究・実験プロジェクト**であり、当面は製品化・一般配布を目的としない
  （philosophy「最初の実験として」より）
- 当面の主な利用者は**作者自身**（ドッグフーディング）
- 想定する最終利用者は**ドメイン知識はあるがコードは書かない人**
- 現時点で優先するのは、他人が使えることより**思想が成立するかの検証**

# 2. もう一度、何が必要か

## 2.1 確定している要件

| # | 要件 | 最小フローでの現れ方 |
|---|---|---|
| 1 | Markdown を正本にする | `master.md` / `lanes/*.md` がすべて |
| 2 | 人間が書いた文章を AI が勝手に変更しない | AI の出力先を `reviews/` に限定 |
| 3 | 設計を Lane へ分割できる | `aide lane <topic>` |
| 4 | AI による質問・提案・矛盾レビュー | `aide review` → `reviews/<topic>-<n>.md` |
| 5 | 人間による明示的な承認 | `aide approve` |
| 6 | 承認時点のハッシュと stale 検出 | `approvedHash` と `aide status` |
| 7 | 判断・差し戻し・統合履歴 | `history.jsonl`（append-only） |
| 8 | 承認済み設計と下書きを区別する | `status` と MCP の `authority` |
| 9 | MCP から実装 AI へ承認済み設計を渡す | `aide_check_design` / `aide_get_section` |
| 10 | Claude/Codex を交換できるバックエンド構造 | 役割名 → コマンドのマッピング |

中心にあるのは一文。

> **承認されていない設計では、実装が始まらない。**

## 2.2 追加を検討すべきもの

10要件を書き出した後に見えてきた、まだ入っていないもの。

### (a) 設計テンプレートに「責任項目」を必須化する

philosophy の最も強い主張はここ。

> セキュリティ、権限、データの保存・送信・削除などは、
> 人間自身が理解し、判断する必要がある。

しかし10要件のどこにも、これを担保する仕組みがない。
レーンのテンプレートに「データの取り扱い」「権限」の欄を**必須**で置き、
空のままでは承認できない（該当しないなら「該当なし」と明示的に書かせる）
という形にするのが、思想を実装に落とす唯一の接点になる。

**これは追加すべきだと考えている。** 小さい割に、思想の中核を守る。

### (b) AI バックエンドが無くても動くこと

今日、クラウドセッションから Codex を呼ぼうとして、
ネットワーク遮断・未インストール・認証情報なしで全滅した。
**AI を呼べない環境は現実に存在する。**

承認・統合・履歴・status・MCP は、AI 抜きで完結すべき。
これは Phase 1 を AI ゼロで設計する理由になる（後述 3.3）。

言い換えると: **AI は補助であって、記録と承認の仕組みは人間だけで回る。**

### (c) レーンの初期テンプレート = 実質的な「設計の型」

空の Markdown を渡されても、人間は何を書けばいいか分からない。
テンプレートが実質的に「AIDE が考える良い設計とは何か」の定義になる。

幸い、このリポジトリの `docs/design/*.md` が既に良い型を持っている。

```
目的 / 背景
対象ファイル
インターフェース / シグネチャ
振る舞い / データフロー
受け入れ条件
エッジケース / エラー処理
テスト方針
スコープ外
```

これをレーンテンプレートに採用する。地味だが、製品価値の中心に近い。

### (d) 人間が関与する深さの調整

philosophy にはこうある。

> 人間が関与する深さは一律でなくてよい。
> AIDE は利用者を固定された役割へ当てはめず、
> レーンや項目ごとに関与する深さを選べることを目指す。

既存実装の `observe-level`（light/strict）がこれにあたるが、最小版では捨てる判断をした。
**思想には含まれるが最小版には無い**という状態なので、
「いつ戻すか」を決めておく必要がある。今は Phase 4 以降の保留とする。

## 2.3 意図的に外すもの

| 外すもの | 理由 |
|---|---|
| ファイル監視の常駐（mdtalk の watch） | 監視・デバウンス・多重実行防止が最も複雑。明示コマンドに統一 |
| 議事録の自動生成、章まとめ | 要件に無い |
| `pool.md` / `pool-archive.md` | 「承認済み未統合」は lane の status で表せる |
| 統合時のマスター AI | 見出し単位の決定的な差し替えにする。Phase 1 が AI ゼロで完結する |
| レーン分割の AI 提案 | 最小版では人間が手動で切る（Phase 4 で復活） |
| VS Code 拡張 | CLI が固まってから |
| observe-level の2段階 | 上記 (d) |

## 2.4 未解決の問い

Codex に投げる予定の7点（`codex-review-request.md`）に加え、今回出たもの。

1. 1〜7 の流れで「承認されていない設計では実装が始まらない」は成立するか。抜け道は
2. AI 出力を `reviews/` に限定する方式と、lane 内の AI 領域限定書き込み、どちらが良いか
3. integrate を決定的処理にすると、master.md はどう劣化するか
4. レビュー → 編集 → レビューのループは収束するか
5. stale の粒度は本文全体のハッシュで妥当か（誤字修正でも承認が無効になる）
6. MCP が誤って `covered` を返す危険はどこにあるか
7. 10要件に足りないもの / さらに削れるものはあるか
8. **(新) 責任項目の必須化は、承認ゲートとして機能するか。形骸化しないか**
9. **(新) レーンテンプレートは、コードを書かない人にとって書けるものか**

# 3. 開発に必要なハーネス・スキル

## 3.1 いま欠けているもの（優先度順）

### 1. `CLAUDE.md` がない ← 最優先

リポジトリの `CLAUDE.md` は、**ローカルにもクラウドにも届く唯一の共有コンテキスト**。
今これが無いため、セッションのたびに README を読み直すところから始まっている。

書くべき内容:
- 設計思想の要約（philosophy へのポインタ）
- コーディング規約（外部依存ゼロ / CommonJS / Node 20+ / 単一ファイル志向）
- テストの動かし方
- 「人間の文は不変」の約束と、それが実装のどこで守られているか

`/init` で雛形が作れる。

### 2. `npm test` が壊れている

`vscode-aide/test/unit/core.test.js` が `../../dist/core.js` を要求するが、
これは TypeScript のビルド成果物。クリーンチェックアウトでは必ず落ちる（122 pass / 1 fail）。

対処のどちらか:
- `package.json` の test を `node --test test/` に絞る（推奨）
- SessionStart hook で先にビルドする

### 3. `.claude/settings.json` がない

SessionStart hook（依存インストール、ビルド）と permissions を置く場所。
クラウドセッションで毎回同じ許可確認が出るのを減らせる。

### 4. `.mcp.json` がない ← 今日判明した本題

`claude mcp add` は既定でローカルスコープ（`~/.claude.json`）に書かれ、
**クラウドセッションには届かない**。公式ドキュメントに明記されている。

```sh
claude mcp add --scope project <name> -- <command>
git add .mcp.json && git commit && git push
```

これでリポジトリの一部になり、クラウドにも届く。

さらに、**AIDE 自身の MCP（`aide mcp`）をここに登録すれば、
AIDE を AIDE で開発できる**。ドッグフーディングとして自然。

### 5. バックエンド不在時の挙動が未定義

`AIDE_OBSERVER_CMD` の既定は `codex` だが、クラウドには存在しない。
「無ければ明示的にエラー」か「AI 無しで進める」かを決める必要がある。
2.2 (b) の結論に従うなら後者。

## 3.2 使えるスキル

| フェーズ | スキル | 使い方 |
|---|---|---|
| 設計 → 実装 | `spec-driven-build` | Markdown 設計 spec を書き、別コンテキストのサブエージェントに実装させる |
| テスト | `test-sonnet-delegate` | 受け入れ条件からテストを導出（実装のミラーにしない） |
| レビュー | `review-sonnet-delegate` | 設計 spec と規約に対して差分をレビュー |
| コミット | `git-haiku-delegate` | staging / commit message / push を委譲 |
| ドキュメント | `docs-haiku-delegate` | README / CHANGELOG の同期 |
| 記録 | `worklog-haiku-delegate` | git 履歴から日報・週報 |
| 環境整備 | `init` | `CLAUDE.md` 生成（3.1-1） |
| 環境整備 | `session-start-hook` | クラウドでテスト・リンタが動くようにする（3.1-2,3） |
| 環境整備 | `update-config` | settings.json / hooks / permissions |
| 品質 | `code-review` / `simplify` / `security-review` | |
| 拡張 | `skill-creator` | AIDE 専用スキル（`/aide-lane` 等）を作る |

**注目すべき点**: `spec-driven-build` の構造
（オーケストレータが設計 spec を書く → 別コンテキストのサブエージェントが実装する）は、
**AIDE がやろうとしていることのミニチュア**である。
AIDE の開発にこれを使うこと自体が、思想の小規模な検証になる。

## 3.3 環境の制約（今日の調査で判明）

| 制約 | 根拠 | 影響 |
|---|---|---|
| クラウドから OpenAI が遮断 | `api.openai.com` / `chatgpt.com` がプロキシで 403 | Codex を観察役に使う設計はクラウドでは動かない |
| ローカルの MCP 設定は届かない | 公式ドキュメント。`~/.claude.json` はマシン上のファイル | `--scope project` + commit が必須 |
| コンテナは使い捨て | セッション終了・無操作で回収 | commit & push しないと消える |
| 環境変数に秘密情報を置けない | 「環境を使う全員が平文で読める」と公式が警告 | API キーの持ち込みは推奨されない |
| stdio 型 MCP はローカルのプロセスを起動する | 仕様 | クラウドから手元のマシンのプロセスは呼べない |

### 結論: ローカルを主、クラウドを従とする

| | ローカル | クラウド |
|---|---|---|
| AI を呼ぶ部分（review / マルチモデル） | ✅ | ❌ Codex 不可、Claude のみ |
| AI を呼ばない部分（承認・ハッシュ・履歴・統合・status） | ✅ | ✅ |
| テスト | ✅ | ✅ |
| MCP の疎通確認 | ✅ | 制限あり |

この表は、**Phase 1 を AI ゼロで設計する理由をもう一つ増やす**。
AI を呼ばない範囲が広いほど、開発できる場所が増える。
これは制約への妥協ではなく、2.2 (b) と同じ結論に別の経路で到達している。
