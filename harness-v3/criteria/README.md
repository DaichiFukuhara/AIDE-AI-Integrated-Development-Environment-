# v3の確認基準 — version 1

DDD由来のモデル観点とAIDE固有の運用観点を分ける。DDDの全パターン採用を求めない。
正式監査・日常確認の頻度と合格条件は[audit](../roles/audit.md)を使う。

| ID | 確認すること | 証拠・適用範囲 |
| --- | --- | --- |
| DDD-01 | 同じcontextで言葉・操作結果の意味が一致する | 固定した定義と正常・例外例。意味変更は利用先へ伝播 |
| DDD-02 | 状態と判断のowner、責任・非責任が明確 | contextと正本、暗黙の他内部への依存がないこと |
| DDD-03 | 常に守る条件と整合の単位・タイミング | 同時更新、重複、取消、中断。実装後は対応する結果 |
| DDD-04 | context間の意味と失敗・再試行・取消が接続する | 契約の正本・両端・版・変換・結果の受理責任 |
| DDD-05 | モデル上の言葉とルールが実装・検証に対応 | 実装後の対応と結果。実装前は確認計画まで |
| AIDE-01 | 目的4階層、条件割当、今回の範囲と委任 | 正本チェーン、対象外、許可、予算、終了条件 |
| AIDE-02 | 主体・操作・結果・理由・制約・未決が分かる | 説明と詳細の一致。本人理解は確認済み/未確認を区別 |
| AIDE-03 | 仕様・定義・実装・証拠・監査の版が対応 | 不変subject、current/baseline、累積差分、stale処理 |

理由付きN/Aを認める。集約は整合性を守る単位が必要な場合、値オブジェクト等は意味を表現する効果がある場合に適用する。
ファイル数・サービス数・特定言語の採用は合格条件ではない。
セキュリティ、性能、データ保護、利用価値等はプロジェクトの受入条件として別途確認する。DDDだけで保証しない。

監査では目的適合、十分性、境界、分解、変更耐性、入力の完全性、検証との接続を横断して確認する。
結果は基準ID・具体的反例・解消条件付きで保存する。好みだけで追加要求を増やさない。
