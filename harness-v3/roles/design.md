# design — 必要な枝を具体化する

記録contextの起草手順。入力は目的、親条件、基準bundle、モデル定義、実験計画。
出力は候補の設計・根拠の対と、条件・参照の対応。

1. root_goalは望ましい成果、subgoalは独立に確認できる価値、approachは解決原理、systemは入出力・状態・失敗を決める。
2. 今回の枝の4階層を揃える。枝数を揃えず、同じ内容の言い換えだけなら親の粒度を直す。
3. 親の条件を子へ割り当て、跨る統合条件は親が持つ。all_ofは全採用子、one_ofは同groupで一つ、optionalは採否を明示する。未採用案は根拠に残す。
4. systemの主親は一つ。再利用はuses_systemsで担当条件を指定する。domain/contextを所有する言語・状態・判断の差から分け、ロール数やサービス数から機械的に分けない。
5. 正本ownerがseamの全契約を持つ。提供・利用側には同じ契約ID・owner・意味版・役割の参照を置く。入力、結果、失敗、再送、取消と意味の変換を定める。
6. 各文書を意味→理由→操作結果→制約→未決→詳細の順で説明する。正常例と重要な例外を一つ以上含める。
7. 計画の実装対象、関連検証、許可、予算が揃ったら[precheck](precheck.md)へ渡す。内部の言語・ライブラリ等は選択範囲を示して委任できる。

v3の候補状態はdraft → ready → checked → committed、またはconflict/rejected/cancelled/stale。
readyは入力が揃った状態、checkedは同じsubjectに必要な確認が済んだ状態。planのcheckedではcurrentを変更しない。
v2の全ノードpublishedを毎回の試作開始条件にはしない。実験対象の親条件・正本・境界は省略しない。

採用後の学びは新しい候補に反映する。局所変更は担当systemと根拠だけを改訂し、全体方針が変わる場合だけmasterも変更する。
